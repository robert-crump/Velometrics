## Issue #178 — Import-time HR recovery metrics: hasHR flag + HRR60/HRR30/avgPower60sAfter per interval
Completed: 2026-09-04

### What was done

First of two children of parent #177 (the second, #179, is blocked on this one and displays what
this issue computes). At import time, extends interval detection to measure heart-rate recovery
after each interval, and adds a session-level HR coverage flag.

**`domain/model/CyclingSession.kt`** — new `hasHR: Boolean = false`, mirroring `hasPower`'s
coverage-threshold pattern; informational only, does not gate per-interval HRR computation.

**`data/fitimport/SessionMetricsCalculator.kt`** — new private `computeHasHR(datapoints)`: true
when at least `POWER_DATA_COVERAGE_THRESHOLD` (10%, reused rather than adding a new HR-specific
constant) of datapoints carry a heart rate reading at all — unlike `computeAvgHeartRate`, a zero
reading still counts as "the sensor reported," matching `hasPower`'s own non-null-only check.
Computed and set directly inside `compute()` (no new parameter needed — unlike `hasPower`, HR
isn't interpolated upstream in `FitImportService`, so the raw datapoints passed to `compute()`
are all `computeHasHR` needs).

**`domain/model/IntervalSession.kt`** — four new nullable fields: `hrr60`/`hrr30`/
`avgPower60sAfter: Int?` and `restBeforeNextIntervalSec: Int?`, all defaulting to null.

**`domain/service/IntervalDetector.kt`** — `buildIntervalSession` now takes the full `datapoints`
list plus `startIdx`/`endIdx`/`nextStartIdx` (rather than a pre-sliced list), so it can read past
an interval's own end. New `computeRecoveryMetrics(datapoints, endIdx)`: reads forward from
`endIdx` bounded only by session end (never by how soon the next interval starts, per the issue's
explicit requirement) — `hrr60`/`hrr30` are the HR drop between the interval's last reading and
the reading nearest 60s/30s later (new `INTERVAL_HRR60_WINDOW_SEC`/`INTERVAL_HRR30_WINDOW_SEC`
constants); `avgPower60sAfter` is mean power over that same 60s window, only counted once a
datapoint at/past the 60s offset is actually reached (so a session ending mid-window yields null,
not a partial-window average passed off as the full figure). `restBeforeNextIntervalSec` is the
actual timestamp gap to `nextStartIdx` (null for the last interval) — truncation is recorded here,
never by nulling the recovery metrics themselves, exactly as the issue specifies for back-to-back
reps with under 60s of rest.

**`data/local/entity/{CyclingSessionEntity,IntervalSessionEntity}.kt`**, **`util/EntityMappers.kt`**
— new columns/fields mapped both directions, all defaulting to false/null so no other construction
site (16 `SessionMetricsCalculator.compute()` call sites, several `IntervalSession(...)` test
sites) needed updating.

**`data/local/VelometricsDatabase.kt`** (v15→16) + **`di/DatabaseModule.kt`** — `MIGRATION_15_16`:
`ALTER TABLE` adds `hasHR INTEGER NOT NULL DEFAULT 0` on `cycling_sessions` and four nullable
`INTEGER` columns on `interval_sessions`. New imports only, no backfill — same precedent as
`MIGRATION_13_14`/`MIGRATION_14_15`.

### Tests

## Issue #176 — Geometric fallback for archetype merge overlap gate (road vs. adjacent bike lane)
Completed: 2026-09-02

### What was done

Follow-up to the previous session's archetype-merge work (`4a4346c`), which explicitly flagged this
as unfixable by threshold tuning alone: `IntervalClusteringService.mergeQualifies`'s overlap gate
compared map-matched edges by literal `(fromNode, toNode)` key equality, so the same physical ride
recorded once on a road and once on the adjacent bike lane/cycleway — represented as two distinct
road-graph edges — could be geometrically near-identical yet share zero edge keys, with no tolerance
setting able to catch it.

Issue #176 itself was filed `ready-for-human` with three open questions (match radius, false-merge
risk, replace-vs-supplement) rather than `ready-for-agent`; per user direction, proceeded using
proposed defaults for all three: reuse the existing `INTERVAL_POINT_MATCH_RADIUS_M` (20m) constant,
accept the parallel/frontage-road false-merge risk as a documented known limitation rather than
adding new mitigation, and have the new test run *alongside* the edge-key test (either signal
sufficient), not replace it.

**`domain/service/IntervalClusteringService.kt`** — `mergeQualifies`'s overlap gate now has a
geometric fallback, evaluated only when the edge-key test doesn't already qualify (short-circuit,
since decoding polylines is the pricier check): new `geometricOverlapRatio(candidate, longer)`
decodes both archetypes' `MapEdge.geometryEncoded` polylines to point lists (each edge already
carries its own geometry, no road-graph lookup needed), builds a `SpatialPointGrid` over `longer`'s
points at `INTERVAL_POINT_MATCH_RADIUS_M`, and computes what fraction of `candidate`'s points have a
neighbor within that radius — the same one-directional coverage-score pattern
`IntervalSimilarity.qualifies` already uses for raw GPS tracks, reused here at the edge-geometry
level per the issue's own suggested direction. `overlapOk` is now `edgeOverlapOk || geometricOverlapOk`,
both gated against the existing `INTERVAL_SUBSET_OVERLAP_THRESHOLD` (0.8). The near-miss diagnostic
log (from `4a4346c`) now reports both ratios (`edgeOverlap=... geometricOverlap=...`, `"skipped"` when
short-circuited) for on-device tuning. No `Constants.kt` changes — reuses two already-defined
constants rather than adding bike-lane-specific ones.

### Tests
Added two cases to `IntervalClusteringServiceTest`: (1) a shorter archetype whose edges use entirely
different node ids from the longer archetype's (zero edge-key overlap) but whose decoded polylines
run ~7m alongside it (well within the 20m radius) now merges — the road/bike-lane scenario the issue
describes; (2) a shorter archetype similarly edge-key-disjoint but offset ~32m away (beyond the
radius) — a genuinely separate parallel road — correctly stays unmerged, guarding against the
fallback being too permissive. `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full
`testDebugUnitTest`: all pass, 315 tests, zero failures/errors across the whole suite (aggregated
test-result XML). No on-device verification this session (no real road-vs-bike-lane duplicate pair
was available to replicate against the live DB, unlike the Camerig data pull that tuned `4a4346c`'s
length tolerance) — flagged in the issue close-out as a residual real-data validation gap, consistent
with the accepted-defaults scope for this pass.

## Issue #175 — Repeat clusters silently dropped when map-matching fails (found via #174)
Completed: 2026-09-02

### What was done

Root cause confirmed by #174's on-device investigation: `IntervalClusteringService.buildArchetype()`
returned `null` whenever `MapMatcher.match()` failed for every candidate representative in a
similarity-confirmed cluster (a short cluster whose GPS track snaps to a single, leaf-pruned road
edge, or a road-graph gap for that segment). Back in `runClustering()`, `.filterNotNull()` then
silently discarded the entire cluster — including intervals that had correctly and confidently
matched each other by GPS similarity — with no user-visible signal, only a `Log.w`.

Implemented the issue's suggested fix direction: fall back to a GPS-only archetype instead of
dropping the cluster.

**`domain/service/IntervalClusteringService.kt`** — `buildArchetype()` no longer returns `null`.
When no cluster member map-matches, it now returns a `CandidateArchetype` with `edges = emptyList()`
and `distanceM`/`startLat`/`startLon`/`endLat`/`endLon` taken directly from the median-length
member's own recorded `IntervalSession` fields (no road-matched geometry needed for these — they're
already stored per-interval). `discardSubsets()` needed no change: an edges-empty candidate never
shares edge keys with anything, so it's never mistakenly discarded as a subset.

**`data/repository/RepeatedIntervalRepositoryImpl.kt`** — `entityToDomain()` had its own copy of
the same bug: `if (edges.isEmpty()) return null` meant a GPS-only archetype (or any archetype whose
stored edge references no longer resolve against the road graph) would vanish again on every
subsequent load, even after being saved successfully. Removed that guard — an archetype with no
resolvable edges now loads fine with its name, intervals, and stats; only `edges` (and therefore the
route-line map preview, which already renders a "No GPS data available" placeholder for an empty
point list) comes back empty.

Not changed: `IntervalMatcher.archetypeTrack()` still can't match new same-route intervals against
a GPS-only archetype incrementally (no edge geometry to compare against), so such an interval waits
for the next full `runClustering()` pass — which re-clusters by GPS similarity from scratch and
will pick it up correctly. This is a temporary staleness, not the reported bug (permanent loss), so
left alone rather than inventing a synthetic edge-geometry representation to close it.

### Tests
Added `IntervalClusteringServiceTest`: a cluster whose fake matcher always returns `null` is still
saved as one archetype (both intervals grouped, `edges` empty, `distanceM`/`startLat`/`endLat` taken
from the median-length member) instead of disappearing. `compileDebugKotlin`,
`compileDebugUnitTestKotlin`, `testDebugUnitTest`: all pass, 310 tests, zero failures/errors across
the whole suite (verified via aggregated test-result XML). No on-device re-verification of the
specific reporter clusters this session (would need the same live-DB replication #174 used); the new
unit test reproduces the exact failure mode (map-matching failure on a similarity-confirmed cluster)
per the issue's own suggested repro approach.

## Issue #173 — Change heart rate zones formula
Completed: 2026-09-01

### What was done

Replaced the HR zone boundaries with Strava's formula: Zone 1|Endurance 0-109 bpm, Zone 2|Moderate
109-144, Zone 3|Tempo 144-161, Zone 4|Threshold 161-179, Zone 5|Anaerobic 179+, all against Strava's
185 bpm reference max HR. As requested, these are expressed as fractions of max HR (0%-100% scale)
rather than hardcoded bpm, so they keep working with each rider's own configured max HR setting
(`UserSettingsRepository.maxHr`), not just 185. No database bump: `hrZoneDistribution` is computed
once at import time (`SessionMetricsCalculator.computeHrZones`) and stored per-session, so already-
imported rides keep their old distribution untouched — only rides imported after this change get the
new boundaries, satisfying the issue's "new imports only" requirement with no migration needed.

**`util/Constants.kt`** — `CyclingConstants.HR_ZONES` boundaries changed from the old ad-hoc
60/70/80/90% splits to 109/185, 144/185, 161/185, 179/185 (Strava's bpm thresholds scaled by its
185 reference max HR). Zone labels ("Zone 1".."Zone 5") and `DEFAULT_MAX_HR` unchanged — only the
fraction cutoffs moved, so no other file (HR zone chart colors/labels, DB schema, JSON keys)
needed touching.

### Tests
Added `SessionMetricsCalculatorTest`: new test asserts `hrZoneDistribution` buckets bpm readings
at and just past each Strava boundary (108/109/143/144/160/161/178/179 with `maxHr = 185`) into the
