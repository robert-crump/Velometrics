## Issue #195 — Test seams: shared fakes package, interfaces for the derived caches, one FlowCache
Completed: 2026-09-18

### What was done

Three mechanical seams flagged by an `/improve-codebase-architecture` review, all in service of making
the four cache-backed ViewModels (`AllTimeStatsViewModel`, `TrainingLoadViewModel`,
`RepeatedRoutesViewModel`, `RepeatedIntervalsViewModel`) testable without standing up Hilt or a real
`ApplicationScope`.

**Shared fakes package** — moved every repository/location fake duplicated verbatim across
`HomeViewModelTest`, `SessionDetailViewModelTest`, and `MapViewViewModelTest` (`FakeIntervalRepository`,
`FakeRepeatedIntervalRepository`, `FakeDropboxSyncCursorRepository`, `FakeMapGraphRepository`, plus the
pre-existing `FakeCyclingSessionRepository`, `FakeLocationSource`, `FakeBestEffortRepository`) into one
new `app/src/test/.../fakes/` package, one fake per interface, and updated every importer (8 test files
beyond the three ViewModel tests: `RepeatedRouteRepositoryImplTest`, `RideRevealEvaluatorTest`,
`RideMilestoneEvaluatorTest`, `SessionComparatorTest`, `RideClassificationServiceTest`,
`PowerCurveAchievementEvaluatorTest`). `SessionDetailViewModelTest`'s local `FakeBestEffortRepository`
stub was dropped in favor of the shared one (behaviorally identical at its default empty-`records`
state). Test-only doubles specific to one test file (e.g. `FailingDeleteCyclingSessionRepository`,
`LatchedDeleteSessionsRepository`) stayed local — only the ones duplicated across files moved.

**Cache interfaces** — `AllTimeStatsCache`, `TrainingLoadCache`, `GlobalAverageCache`,
`RepeatedRoutesCache`, `RepeatedIntervalsCache` are now interfaces in `data/cache`, each implemented by
a `*Impl` class (still the `@Singleton @Inject constructor` doing the real Flow wiring), bound via a new
`di/CacheModule.kt` `@Binds` module — the same interface/impl/`@Binds` pattern `RepositoryModule`
already uses for repositories. Every ViewModel and `VelometricsApplication`'s eager-init injection site
kept referencing the cache by its original name, since that name now resolves to the interface — no
call-site changes needed outside the cache files themselves and the new module.

**One `FlowCache`** — `RepeatedRoutesCache`/`RepeatedIntervalsCache` were byte-identical modulo type, so
their hot-`StateFlow`-plus-`isLoading` shape moved into a new generic `HotFlowCache<T>`
(`data/cache/HotFlowCache.kt`); `RepeatedRoutesCacheImpl`/`RepeatedIntervalsCacheImpl` are now thin
wrappers around one each. `debounce(300)`'s value and rationale, previously copy-pasted across
`AllTimeStatsCache`/`TrainingLoadCache`/`GlobalAverageCache`'s KDocs, now live once in a new
`data/cache/CacheDebounce.kt` (`CACHE_DEBOUNCE_MS` constant + a `Flow<T>.debounced()` extension); all
three plus `HotFlowCache` call the shared extension instead of a bare `.debounce(300)`. Explicit decision
on the issue's open question: `HotFlowCache` **does** debounce (previously neither Repeated* cache did,
with no stated reason) — clustering does `deleteAll()` then one `saveX()` per cluster on every run
(see `RouteClusteringService`/`IntervalClusteringService`), the same per-write-storm shape the other
three caches' debounce already guards against, just triggered by a clustering pass instead of a bulk
import.

**Smoke tests** — one test class each for the four ViewModels that had none before, exercising the new
interface seam directly: `AllTimeStatsViewModelTest`, `TrainingLoadViewModelTest` (both trivial —
`uiState` is a direct passthrough of the injected cache's `StateFlow`, verified against a
`FakeAllTimeStatsCache`/`FakeTrainingLoadCache`), `RepeatedRoutesViewModelTest`,
`RepeatedIntervalsViewModelTest` (cover the cache passthrough plus sort/`isLoading` wiring and that
`refresh()` invokes the injected clustering service and clears `isRefreshing`, using
`FakeRepeatedRoutesCache`/`FakeRepeatedIntervalsCache` and a relaxed/`coEvery`-stubbed
`RouteClusteringService`/`IntervalClusteringService` mock — no Hilt, no `UserSettingsRepository`'s real
Android `DataStore`, no `ApplicationScope`).

### Tests
New: `AllTimeStatsViewModelTest` (2), `TrainingLoadViewModelTest` (2), `RepeatedRoutesViewModelTest` (3),
`RepeatedIntervalsViewModelTest` (3) — 10 new cases, all exercising the fakeable-interface seam this
issue introduced. `compileDebugKotlin`, `compileDebugUnitTestKotlin`, `assembleDebug` (confirms the new
`CacheModule` `@Binds` graph resolves), full `testDebugUnitTest`: all pass, 379 tests, zero
failures/errors across the whole suite (aggregated test-result XML). No on-device verification this
session (no emulator/device attached) — this issue is a pure test-seam refactor with no UI or behavior
change, so the unit suite is the relevant feedback loop.

## Issue #194 — Bulk delete rides from Home (multiselect)
Completed: 2026-09-07

### What was done

Third slice of #187: multiselect bulk delete on the Home ride list, reusing #193's shared
`ConfirmDialog` and the same "no recluster here" rule #192/#193 established for single-ride delete.

**`data/local/dao/CyclingSessionDao.kt`** — new `deleteById(id)` (`@Query DELETE ... WHERE id =
:id`) and `deleteSessions(ids: List<Long>)`, a `@Transaction`-annotated default method that loops
`ids.forEach { deleteById(it) }`. Room wraps the whole loop in one transaction, so a failure
partway through rolls back every delete already issued in that call, rather than leaving some
sessions deleted and others not. FK `ON DELETE CASCADE` (already in place for #193's single-session
delete) removes each deleted session's `interval_sessions`/`session_best_efforts` rows the same way.
**`domain/repository/CyclingSessionRepository.kt`** / **`data/repository/CyclingSessionRepositoryImpl.kt`**
— new `deleteSessions(ids: List<Long>)`, a thin pass-through to the DAO method.
**`data/repository/FakeCyclingSessionRepository.kt`** (test) — matching fake implementation
(`sessions.removeAll { it.id in ids }`).

**`ui/screens/home/HomeViewModel.kt`** — new selection-state surface: `selectionMode:
StateFlow<Boolean>`, `selectedSessionIds: StateFlow<Set<Long>>`, `deleteError: StateFlow<String?>`.
`enterSelectionMode(sessionId)` (long-press: turns on selection mode with just that card selected),
`toggleSessionSelected(sessionId)` (add/remove from the set; no-ops outside selection mode),
`exitSelectionMode()` (close/back: clears both the mode flag and the selection), `clearDeleteError()`.
`deleteSelectedSessions()` calls `sessionRepository.deleteSessions(ids)` on
`Dispatchers.IO`: on success calls `exitSelectionMode()` (Home's list updates on its own via the
existing Flow-backed `getAllSessionSummaries()` query); on a caught `Exception` sets `deleteError =
"Couldn't delete rides"` and leaves selection mode + the selection untouched so the user can retry.
Deliberately does **not** call `recluster()` — out of scope per the issue, matching #193's
single-delete precedent; that stays on #192's lazy pull-to-refresh path.

**`ui/screens/home/HomeScreen.kt`** — `BackHandler(enabled = selectionMode) {
viewModel.exitSelectionMode() }`. `Scaffold`'s `topBar` now branches on `selectionMode`: the normal
title/overflow `TopAppBar` unchanged, or a contextual bar (close/X `navigationIcon`, "N selected"
title, trash-can `actions` icon disabled when nothing is selected) while selecting. Tapping the
trash icon opens the shared `ConfirmDialog` ("Delete rides?" / "Delete N rides? This can't be
undone." / "Delete"); confirming calls `deleteSelectedSessions()`. A new `LaunchedEffect(deleteError)`
shows it on the existing `snackbarHostState` (same shape as the pre-existing `dropboxSyncMessage`
effect) and clears it after. `SessionCard` gained `selected`/`onLongClick` params: the card's
`onClick` shorthand was replaced with `Modifier.combinedClickable(onClick, onLongClick)` (needed for
long-press), a selected card gets a `secondaryContainer`-tinted background plus a leading
`Icons.Filled.CheckCircle`, and the list's `onClick` now toggles selection in selection mode instead
of navigating. Out of scope, per the issue: recluster-on-delete, undo, and hiding the import FAB
while selecting.

### Tests
New `CyclingSessionDaoTest` (Robolectric, native SQLite, real `VelometricsDatabase` — same setup as
`CyclingAssetDatabaseFixtureTest`/`VelometricsMigrationTest`, not a fake): `deleteSessions` cascades
`interval_sessions`/`session_best_efforts` for every id in a mixed batch while leaving an
unselected session untouched; a second case exercises the same `db.withTransaction` + `deleteById`
mechanism `@Transaction` relies on directly (no seam exists to inject a failure inside the
interface's own generated loop) and confirms a `RuntimeException` thrown after two deletes have
already been issued rolls both back, proving the underlying rollback guarantee `deleteSessions`
depends on.
Five new cases in `HomeViewModelTest`: `enterSelectionMode`/`toggleSessionSelected` (add, remove,
no-op outside selection mode)/`exitSelectionMode` state transitions, and `deleteSelectedSessions`
on both a `LatchedDeleteSessionsRepository` success (sessions removed, selection mode exits, no
error) and forced-failure path (error message set, selection mode + selected ids left untouched for
retry) — same real-`Dispatchers.IO`-with-`CountDownLatch` pattern `syncDropbox`'s tests already use,
since `deleteSelectedSessions` also dispatches off the test dispatcher.
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, `assembleDebug`, full `testDebugUnitTest`: all
pass, 358 tests, zero failures/errors across the whole suite (aggregated test-result XML) — 351
prior + 7 new (2 DAO + 5 HomeViewModel). No on-device verification this session (no emulator/device
attached); the selection/delete/error branching is fully covered by the new unit tests, and the
long-press/contextual-TopAppBar/dialog wiring is otherwise-standard Compose plumbing with no Compose
UI test harness in this project (same residual gap as every prior UI-touching pass in this repo's
history).

## Issue #192 — Cluster hygiene: keep Repeated Routes/Intervals correct after ride deletion
Completed: 2026-09-07

### What was done

Second slice of #187: keeps Repeated Routes/Intervals correct after #193's ride-delete, without
delete itself triggering a recompute (clustering's full-recompute cost stays off the delete path).

**`ui/screens/home/HomeViewModel.kt`** — `syncDropbox()`'s `recluster()` call moved into the
`finally` block (was: only inside the `DropboxSyncResult.Completed` branch, and only when an import
actually succeeded). `finally` runs on every path — not connected, needs reauth, or a completed sync
regardless of outcome — so pull-to-refresh now reclusters unconditionally, becoming the general
"resync cluster state" action for a user who just deleted a ride. The existing "Connect Dropbox in
Settings" message still shows exactly as before; only the recluster gating changed. Both
`RouteClusteringService.runClustering()`/`IntervalClusteringService.runClustering()` already do a
full recompute straight from the current DB state, so a deleted session/interval simply isn't in
their input on the next pass — no clustering-service change needed for this half.

**`util/Constants.kt`** — new `CyclingConstants.ROUTE_CLUSTER_MIN_GROUP_SIZE = 3`, hoisted out of
`RouteClusteringService`'s previously-private `MIN_GROUP_SIZE` so the repository layer (below) can
enforce the same floor. `RouteClusteringService` now defines its own `MIN_GROUP_SIZE` as a reference
to the shared constant — no behavior change there.

**`data/repository/RepeatedRouteRepositoryImpl.kt`** — `entityToDomain`'s existing
`ids.mapNotNull { sessionMap[it] }` already silently drops a stale id (a session deleted since the
last recluster; `RepeatedRouteEntity.sessionIds` carries no FK); the gap was that the group was only
hidden once *every* member went stale (`sessions.isEmpty()`). Changed the guard to
`sessions.size < ROUTE_CLUSTER_MIN_GROUP_SIZE`, so a route whose surviving count falls to 1 or 2
(below clustering's own minimum group size) is hidden entirely, same as a group that never reached
that size during clustering — rather than rendering an under-strength "repeated" route.

**`data/repository/RepeatedIntervalRepositoryImpl.kt`** — no behavior change; `entityToDomain`
already filters stale ids the same way and correctly hides only a fully-emptied entry, which is
already right here since `IntervalClusteringService` has no minimum group size (documented/tested
as "no minimum group size" — a lone surviving interval is a valid archetype on its own). Added a
comment explaining why this file needed no floor-check unlike the route one.

Out of scope, per the issue: `IntervalSessionEntity.achievementRank`/`achievementScope` staleness
after a rank-holder is deleted (pre-existing, accepted, unrelated to this issue's cluster-hygiene
scope).

### Tests
`RepeatedRouteRepositoryImplTest` (new, 3 cases, `mockk<RepeatedRouteDao>` + real
`FakeCyclingSessionRepository`): a route with one stale member id (4 → 3 survivors) still resolves
with the remaining valid sessions; a route whose survivor count drops to 2 (below the minimum of 3)
is hidden entirely; a route with zero survivors is hidden (not just filtered down).
`RepeatedIntervalRepositoryImplTest` (new, 2 cases, `mockk<RepeatedIntervalDao>`/`IntervalRepository`/
`MapGraphRepository`): a repeated interval with one stale member id (3 → 2 survivors) still resolves
with the remaining valid intervals (no minimum group size, unlike routes); one with zero survivors
is hidden. `HomeViewModelTest` (new, first test for this ViewModel; 3 cases, real `CountDownLatch`
wait rather than virtual time since `syncDropbox` explicitly dispatches onto the real
`Dispatchers.IO`, not a swappable test dispatcher): `syncDropbox` reclusters (both services) when
Dropbox is disconnected, when connected but sync finds nothing new, and when Dropbox needs reauth —
each previously would have skipped the recluster call entirely.
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, `assembleDebug`, full `testDebugUnitTest`: all
pass, 351 tests, zero failures/errors across the whole suite (aggregated test-result XML) — 341
prior + 8 new (3 route-repo + 2 interval-repo + 3 HomeViewModel) + 2 more from other work landed on
main since #193's count was recorded. No on-device verification this session (no emulator/device
attached); the resolve/hide branching and the unconditional-recluster wiring are fully covered by
the new unit tests.

## Issue #185 — Repeated-interval achievement badge in the name row
Completed: 2026-09-06

### What was done

New import-time achievement snapshot, scoped to one `RepeatedInterval`'s own reps (never against
other archetypes or plain rides), surfaced in the repeated-interval name row.

**`domain/model/IntervalAchievement.kt`** (new) — `AchievementScope` enum (`ALL_TIME`/`THIS_YEAR`)
and `IntervalAchievement(rank, scope, year)`, per the issue's illustrative shape.

**`domain/service/IntervalAchievementEvaluator.kt`** (new) — `evaluate(interval, reps)`, where
`reps` is the archetype's full, already-updated rep list (including `interval` itself). Ranks by
raw `avgSpeedKmh` via the same count-strictly-greater-then-+1 shape `RankedMetricEvaluator` uses for
ride-level achievements, but over the in-memory rep list rather than a repository query. Gates on
`reps.size < 3` (total reps, not year-scoped) before evaluating either scope. Tries `ALL_TIME`
first (over all reps) and only falls back to `THIS_YEAR` (reps whose `startTimestamp` falls in the
same calendar year, system default zone) when `ALL_TIME` isn't top-3 — so a rep qualifying in both
is recorded as `ALL_TIME`, matching the issue's precedence rule. Returns `null` past 3rd place in
both scopes.

**`domain/model/IntervalSession.kt`** / **`data/local/entity/IntervalSessionEntity.kt`** — new
nullable `achievementRank: Int?` / `achievementScope: AchievementScope?` (entity: `String?`, the
enum's `.name`) fields. **`util/EntityMappers.kt`** — mapped both directions
(`AchievementScope.valueOf(...)` / `.name`). **`data/local/VelometricsDatabase.kt`** — version 17 →
18. **`di/DatabaseModule.kt`** — `MIGRATION_17_18` (two nullable `ALTER TABLE ADD COLUMN`s, same
shape as `MIGRATION_15_16`/`MIGRATION_16_17`), added to `addMigrations(...)`.

**`domain/service/IntervalMatcher.kt`** — now also takes `IntervalRepository`. Right after grouping
each import batch's newly-matched intervals under their archetype and building `updatedReps =
archetype.intervals + matched` (the archetype's full, current rep list), each matched interval is
run through `IntervalAchievementEvaluator.evaluate(interval, updatedReps)`; a non-null result is
persisted via `intervalRepository.updateInterval(interval.copy(achievementRank = ...,
achievementScope = ...))` before the archetype itself is saved. This is the "compute once, right
after `matchToRepeatedIntervals` groups the new interval" snapshot the issue calls for — it's never
recomputed afterward, so a later rep beating an earlier one doesn't retroactively change the
earlier snapshot. Historical intervals (matched before this change) simply never went through this
path, so they're left with null achievement fields — no backfill, matching the HRR60/#178
precedent.

**`ui/components/IntervalListCard.kt`** — new private `achievementLabel(interval)` helper: returns
`"3rd best 2026"` / `"3rd best all-time"` (or `null` when the interval carries no achievement
snapshot) — the year is derived from `interval.startTimestamp`'s own calendar year at render time,
not persisted separately, since a past rep's year never changes. The name row now renders
`"${ref.name} | ${achievementLabel}"` when a snapshot exists, else the plain `ref.name` unchanged.

### Tests
`IntervalAchievementEvaluatorTest` (new, 6 cases): the minimum-reps gate (2 reps records nothing
even for the fastest), the exact rank-3/rank-4 boundary among 5 reps, ties (two reps tied for
fastest both rank 1st, a third ranks 3rd — not 2nd), a rep qualifying in both scopes at once
recording `ALL_TIME`, a rep that only qualifies `THIS_YEAR` recording that scope + the correct
literal year, and a rep beaten too many times in both scopes getting nothing.
`VelometricsMigrationTest` gained `migrate 17 to 18 adds nullable achievementRank and
achievementScope columns defaulting to null`, mirroring the 16→17 test shape.
`IntervalMatcherTest`'s constructor call updated for `IntervalMatcher`'s new `IntervalRepository`
parameter (mocked, relaxed) — its own tests only exercise the pure `matchIntervals` function, so no
behavior there needed changing.
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, `assembleDebug`, full `testDebugUnitTest`: all
pass, 339 tests, zero failures/errors across the whole suite (aggregated test-result XML) — 332
prior + 7 new (6 evaluator + 1 migration). No on-device verification this session (no
emulator/device attached); the ranking/persistence logic is fully covered by the new unit tests, and
the name-row rendering is a small pure-string helper with no Compose UI test harness in this
project (same residual gap as every prior UI-touching pass in this repo's history).
