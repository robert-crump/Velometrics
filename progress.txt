## Issue #160 — Ride Reveal: power-curve best-effort achievements
Completed: 2026-08-29

### What was done

Only `ready-for-agent` issue in the queue — the other half of the Ride Reveal Tier 1 achievement
pair alongside #159 (ride-level milestones), which landed earlier this session and gave this one's
milestone-beats-power-curve tie-break something genuine to verify against instead of a contrived
resolver-only test. Mirrors #159's rank-query shape almost exactly ("count of best efforts with a
strictly greater value, plus 1", scoped by an optional `since` bound), applied to
`BestEffortCalculator`'s 5s/1min/5min/20min power-curve fields instead of raw session stats.

One structural difference from #159: a ride-level metric (distance, elevation, speed) lives right
on the `CyclingSession` object `RideMilestoneEvaluator.candidates()` already receives, but power-curve
bests live in a separate `session_best_efforts` row that `RideRevealEvaluator` wasn't fetching.
Added `BestEffortRepository.getForSession(sessionId)` (a single-row DAO lookup by `sessionId`, mapped
to the same `BestEffortValues` domain type the calculator already produces) so
`PowerCurveAchievementEvaluator.candidates(sessionId, sessionStart)` can look up the ride's own bests
before ranking them.

**`data/local/dao/SessionBestEffortDao.kt` (+ `BestEffortRepository`/Impl, `FakeBestEffortRepository`)**
- `getBySessionId(sessionId): SessionBestEffortEntity?` and four `countBestEffortsWithGreaterPower{5s,
  1m,5m,20m}(power, sinceEpochMs: Long?)` queries, each `SELECT COUNT(*) FROM session_best_efforts sbe
  JOIN cycling_sessions cs ON cs.id = sbe.sessionId WHERE sbe.powerX > :power AND (:sinceEpochMs IS
  NULL OR cs.sessionStart >= :sinceEpochMs)` — same join-for-the-date-scope shape #159 used, needed
  here because `session_best_efforts` itself has no date column. A NULL power value (no power meter
  that ride, or the ride was shorter than the duration) is excluded automatically by SQLite's
  NULL-comparison semantics, same as #159's NULL-elevation handling. No new index (same personal-scale
  non-issue precedent). `FakeBestEffortRepository` computes both `getForSession` and the four counts
  directly off its existing `records: MutableList<BestEffortRecord>` — that type already carries
  `sessionId`, `sessionStart`, and every power field, so no new fake-side storage was needed.

**`domain/service/PowerCurveAchievementEvaluator.kt`** (new, `@Singleton`, injects `BestEffortRepository`)
- `candidates(sessionId, sessionStart): List<RideRevealCandidate>`: fetches the ride's own best-effort
  row via `getForSession`; returns `emptyList()` outright if there isn't one (no power meter that
  ride). Builds a metric per non-null duration (5s/1m/5m/20m — up to 4, fewer if some durations are
  null e.g. a shorter ride missing 20-min), each carrying its own count-greater-than query and a
  headline label ("5-second power" etc). For each metric, queries both scopes and registers a
  `POWER_CURVE_BEST_EFFORT`-family candidate for every scope where `count + 1 <= 3` — up to 8
  candidates per ride. Headline template ("Your {best|2nd-best|3rd-best} {duration} power {ever|this
  year}!") mirrors #159's ordinal-superlative approach.

**`domain/service/RideRevealEvaluator.kt`**
- Constructor gained `PowerCurveAchievementEvaluator`; `evaluate()` now passes
  `milestoneEvaluator.candidates(session) + powerCurveEvaluator.candidates(session.id,
  session.sessionStart) + fallbackCandidate(session)` to the resolver. Class doc comment updated to
  name both Tier 1 sources as landed rather than one pending.

## Issue #159 — Ride Reveal: ride-level milestone achievements
Completed: 2026-08-29

### What was done

Second Ride Reveal slice, picked over #160 (power-curve best-effort achievements) even though
both were unblocked by #158 landing earlier this session — #160's own acceptance criteria needs a
real ride-level milestone candidate to exist to verify the milestone-beats-power-curve tie-break,
so building this one first gives that check something genuine to run against instead of a
contrived resolver-only test.

Rank query shape follows the design doc's own suggestion almost exactly: "rank = count of rides
with a strictly greater value, plus 1", scoped by an optional `since` bound (null = all-time, or
the ride's own calendar-year start for "this year"). Deliberately used the ride's own
`sessionStart` year (via `ZoneId.systemDefault()`), not wall-clock "now" — the two coincide for a
ride that just synced (the only time this runs today), but stays correct if a batch is ever
evaluated after the fact instead of live. Confirmed the acceptance criteria's "no minimum
sample-size threshold" assumption is genuinely load-bearing with a dedicated test: a ride with
only 3-4 total rides ever, ranking last of them, still registers as a "3rd place" milestone.

**`data/local/dao/CyclingSessionDao.kt` (+ `CyclingSessionRepository`/Impl, `FakeCyclingSessionRepository`)**
- Three new `countSessionsWithGreater{Distance,ElevationGain,AverageSpeed}(value, sinceEpochMs:
  Long?)` queries, each `SELECT COUNT(*) ... WHERE metric > :value AND (:sinceEpochMs IS NULL OR
  sessionStart >= :sinceEpochMs)`. No new index (matches #156/#158 precedent — a non-issue at this
  app's personal ride-count scale). A NULL `elevationGainM` column, or a `netDurationSec <= 0` row,
  is excluded from the "greater" count automatically by SQLite's NULL-comparison semantics for the
  first two, and by an explicit `netDurationSec > 0` guard for the average-speed query (computed
  in-SQL as `distanceKm / netDurationSec * 3600`, not a stored column) — no separate null-handling
  branch needed in the DAO. Repository interface takes `since: Instant?`, converting to epoch
  millis only at the Impl boundary, matching `getMaxSessionStart`'s existing `Instant`/`Long` split.
  `FakeCyclingSessionRepository` mirrors the same semantics with plain Kotlin filtering.

**`domain/service/RideMilestoneEvaluator.kt`** (new, `@Singleton`, injects `CyclingSessionRepository`)
- `candidates(session): List<RideRevealCandidate>`: builds a small in-memory list of the 2-3
  trackable metrics for this ride (distance always; elevation only if `elevationGainM != null`;
  average speed only if `netDurationSec > 0`), each carrying its own count-greater-than query, a
  headline vocabulary (superlative + noun, e.g. "longest"/"ride"), and its raw value. For each
  metric, queries both scopes (all-time and this-year) and registers a `RIDE_MILESTONE`-family
  candidate for every scope where `count + 1 <= 3` — up to 6 candidates per ride, all handed to
  `RideRevealEvaluator` for `RideRevealResolver` to pick among. Headline template
  ("Your {ordinal-superlative} {noun} {ever|this year}!") reuses the same superlative word for rank
  1 and prefixes "2nd-"/"3rd-" for ranks 2/3 ("Your longest ride ever!" ->
  "Your 2nd-longest ride ever!"), which reads naturally for all three metric nouns without
  per-metric-per-rank copy.

**`domain/service/RideRevealEvaluator.kt`**
- Constructor gained `RideMilestoneEvaluator`; `evaluate()` now passes
  `milestoneEvaluator.candidates(session) + fallbackCandidate(session)` to the resolver instead of
  just the fallback alone. Class doc comment updated to stop saying "today only the fallback is
  registered" and name both this and the still-pending #160 source.

### Tests

ranks 1st all-time on all 3 metrics; a ride beaten by 3 others on a metric doesn't qualify on it

## Issue #158 — Ride Reveal: trigger + guaranteed fallback
Completed: 2026-08-29

### What was done

First slice of the Ride Reveal feature (design doc: `docs/ideas/ride-reveal-hero.md`, not yet
committed before this session). Picked over #159/#160 since both are explicitly blocked on this
one (they plug into the resolver/trigger this issue builds). Read the design doc's trigger-condition
section closely since it's the crux of the issue and has a subtle backfill trap: "identify the
single most-recently-imported file's ride" turns out to mean the *chronologically* newest ride
actually imported in the batch (by parsed FIT start-time), not the last file processed by name/
order — the doc's own clarifying sentence ("not filename or Dropbox processing order") only makes
sense under that reading, since `DropboxSyncService` sorts entries by filename before importing.
The backfill guard falls out for free from comparing against a *pre-sync baseline*: captured once
per batch via `getMaxSessionStart()` *before* any file in that batch is imported; a null baseline
(empty DB) means "never reveal," so a first-time Dropbox connect or fresh-install backfill of
hundreds of historical rides can't trigger it no matter which file in that batch is chronologically
last, since there's no pre-existing max to be "later than."

**`domain/repository/CyclingSessionRepository.kt` (+ Impl, DAO, `FakeCyclingSessionRepository`)**
- New `getMaxSessionStart(): Instant?` — a plain `SELECT MAX(sessionStart)`, null on an empty table.
  No new index; matches the design doc's explicit call that this is a non-issue at personal ride-
  count scale.

**`data/fitimport/ImportResult.kt`, `data/fitimport/FitImportService.kt`**
- `ImportResult.Success` gained a `sessionStart: Instant` field (the already-computed
  `session.sessionStart`, no extra DB round-trip) so callers can identify the batch's
  chronologically-newest imported ride without re-fetching every session.

**`domain/model/RideRevealCandidate.kt`** (new)
- `RideRevealScope` (ALL_TIME, THIS_YEAR), `RideRevealFamily` (RIDE_MILESTONE,
  POWER_CURVE_BEST_EFFORT, FALLBACK), and `RideRevealPriority(scope, rank, family):
  Comparable<RideRevealPriority>` implementing the design doc's exact tie-break ordering (scope,
  then rank, then family) via enum-ordinal comparison — declaring each enum's entries in
  best-first order makes the `compareTo` a one-liner per field, no explicit weight table needed.
  `RideRevealPriority.FALLBACK` is a companion constant (`THIS_YEAR`/`Int.MAX_VALUE`/`FALLBACK`)
  that's guaranteed to lose to any real 1st-3rd achievement in any scope, verified in
  `RideRevealResolverTest`. `RideRevealCandidate(headline, priority)` — deliberately just those two
  fields, matching the issue's "a label plus a priority key" description, so #159/#160 don't need
  any new shape to plug into.

**`domain/service/RideRevealResolver.kt`** (new)
- `resolve(candidates: List<RideRevealCandidate>): RideRevealCandidate` — a pure `reduce` picking
  the lowest-priority (best) candidate; throws on an empty list (callers always pass at least the
  fallback).

**`domain/service/RideRevealEvaluator.kt`** (new, `@Singleton`, injects `CyclingSessionRepository`)
- `captureBaseline()`: thin wrapper on `getMaxSessionStart()`, called once per batch *before* import
  starts.
- `evaluate(results, baseline)`: null baseline -> null (backfill guard). Otherwise takes
  `results.filterIsInstance<ImportResult.Success>().maxByOrNull { it.sessionStart }` (ignores
  `Error`/`AlreadyImported`/skipped-`SmallFile` entries) — if that ride's start isn't after
  `baseline`, returns null (routine sync, nothing newer than what already existed). Otherwise fetches
  the full `CyclingSession`, builds the single Tier 2 fallback candidate (static "Nice ride!"
  headline, `RideRevealPriority.FALLBACK`), resolves it (trivially, since it's the only candidate
  today), and returns `RideRevealContent(sessionId, headline, distanceKm, netDurationSec,
  elevationGainM)`. This is the one place #159/#160 will extend: add their candidate(s) to the same
  list before calling `RideRevealResolver.resolve`.

**`ui/screens/home/HomeViewModel.kt`**
- New `ImportUiState.RideReveal(content: RideRevealContent)`, shown instead of `Done`
  (`importFromUris`) or the Dropbox snackbar (`syncDropbox`) when `RideRevealEvaluator.evaluate`
  returns non-null.
- `importFromUris`: now accumulates every file's `ImportResult` into a list (previously only tracked
  `lastResult`, overwritten each iteration) so the evaluator can see the whole batch; captures the
  baseline before the loop starts. The existing early-return-on-unreadable-file quirk (aborts the
  rest of the batch, a pre-existing behavior out of scope here) is preserved via `break` instead of
  `return@withLock`, with identical downstream behavior since both paths fall through to the same
  final-state assignment now.
- `syncDropbox`: captures the baseline immediately before `dropboxSyncService.sync()`; on
  `DropboxSyncResult.Completed`, evaluates the reveal before falling back to the existing
  `buildSyncMessage`/snackbar path, so pull-to-refresh gets the same reveal behavior as manual
  import without duplicating the trigger logic.

**`ui/screens/home/HomeScreen.kt`**
- New `RideRevealSheet` (`ModalBottomSheet`, `skipPartiallyExpanded = true`): headline text, a
  distance/duration/elevation stat row (elevation cell omitted when null, matching how the rest of
  the app treats a missing `elevationGainM`), and a "View ride" button that dismisses the sheet and
  navigates via the screen's existing `onSessionClick`. Rendered alongside the pre-existing
  `SmallFileWarning` dialog block, gated on the same `currentState` snapshot.

**`docs/ideas/ride-reveal-hero.md`**: committed for the first time this session (existed untracked
in the working tree beforehand) since it's the design rationale this and the two follow-up issues
point to.

### Tests
New `RideRevealResolverTest` (6 cases: single-candidate trivial win, achievement beats fallback
regardless of list order, all-time beats this-year regardless of rank, lower rank wins within a
scope, ride-milestone beats power-curve within equal scope+rank, empty list throws) and
`RideRevealEvaluatorTest` (8 cases, via `FakeCyclingSessionRepository`: null baseline on an empty
DB, baseline = latest existing start, fires when later than baseline, doesn't fire when not later,
doesn't fire on a backfill into an empty DB even for the batch's newest ride, picks the
chronologically-newest batch member rather than the last one in the results list, ignores
non-`Success` results when picking the batch's newest ride, no successes never fires).
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, `compileDebugAndroidTestKotlin`, `assembleDebug`,
full `testDebugUnitTest --rerun-tasks` (matching the known Gradle env-var/test-filter stale-cache
quirk from #135): all pass (242 tests, up from 228 — 14 new), no regressions. No on-device
verification this session (needs a real device with Dropbox configured and two ordered rides to
exercise the reveal end-to-end; the trigger/resolver logic is fully covered by the new unit tests,
and the sheet itself is a straightforward `ModalBottomSheet` with no novel rendering risk).

## Issue #154 — Cardiac efficiency: Diagramm (Cardiac Drift chart)
Completed: 2026-08-02

### What was done

Only `ready-for-agent` issue in the queue. The issue itself was two open questions (bucket size,
low-power handling); the maintainer had already resolved the full design via a `/grill-me` session
posted as a comment before this session started, so this was implementation against that finalized
plan rather than a fresh design pass.

One genuine ambiguity remained in the plan text: "following the Fat Efficiency pattern — no schema
change, no persisted raw time series." Fat Efficiency's own pattern *does* persist its output via new
nullable columns (a real migration), and nothing else in the schema could hold per-bucket drift data
for the chart to read back on a later visit to Session Detail. Asked the maintainer directly rather
than guessing: confirmed "no schema change" was shorthand for "no new table, no raw per-sample
series" (contrasted against a rejected alternative of persisting the full per-second stream), not
"literally zero new columns" — so this adds two new nullable columns exactly like
`fatEfficiencyHistogram`/`fatEfficiencyScore` did.

**`util/Constants.kt`**
- `CARDIAC_DRIFT_BUCKET_SEC` (600), `CARDIAC_DRIFT_MIN_RIDE_SEC` (3600), the 25%-FTP exclusion
  fraction, and the 50% bucket-drop fraction.

**`domain/model/CardiacDriftBand.kt`** (new)
- `GOOD`/`NORMAL`/`SIGNIFICANT` enum with `fromPercent(decouplingPercent)`, boundaries at 5%/10%
  matching the plan's classic-Coggan bands.

**`data/fitimport/SessionMetricsCalculator.kt`**
- New `computeCardiacDrift`: splits the ride into fixed 600-second buckets (a trailing partial
  bucket is absorbed into the last full bucket via `coerceIn(0, bucketCount - 1)` on the bucket
  index, rather than kept as its own short bucket); per bucket, samples with raw power below 25% FTP
  are excluded from that bucket's power/HR averages (deliberately using raw `dp.power`, not the
  effective/substituted power used for fat-burn calculations elsewhere in this file — using the
  substituted value would defeat the exclusion, since coasting/descending streaks get backfilled
  with a plausible non-zero wattage there); a bucket is dropped (absent from the result map) if more
  than half its samples were excluded this way. Baseline = avg EF (power/HR) over first-half buckets
  (by bucket index, `bucketCount / 2`); decoupling % = decline from that baseline to the second-half
  average. Returns null outright if `totalDurationSec < 3600` (the 60-minute/6-bucket gate lives
  here, not in the UI) or if either half ends up with zero surviving buckets. Only invoked when
  `hasPower && avgHeartRate != null`, matching the existing gating convention for `fatEfficiencyScore`
  etc.

**`domain/model/CyclingSession.kt`, `data/local/entity/CyclingSessionEntity.kt`, `util/EntityMappers.kt`**
- New `cardiacDriftBuckets: Map<String, Double>?` (bucket index as String key -> % of first-half
  baseline EF; a dropped bucket is simply absent, not a zero) and `cardiacDriftPercent: Double?`.
  JSON (de)serialization follows the exact `hrZoneDistribution`/`fatEfficiencyHistogram` pattern, with
  a separate `Map<String, Double>` `TypeToken` alongside the existing `Map<String, Int>` one (the other
  histograms are all integer counts; this one needs fractional precision).

**`data/local/VelometricsDatabase.kt`, `di/DatabaseModule.kt`**
- DB version 12 -> 13. `MIGRATION_12_13`: two plain `ALTER TABLE ADD COLUMN` statements, no data
  transform needed (purely additive, both nullable) — same shape as `MIGRATION_8_9`/`MIGRATION_9_10`,
  which also didn't get a dedicated migration test for the same reason (nothing to get wrong beyond
  what Room's own schema validation already catches).

**`ui/components/CardiacDriftChart.kt`** (new)
- Line chart (a deliberate departure from this screen's existing bar-chart idiom, per the plan) — one
  Canvas per session, plotting each surviving bucket's % of baseline with a dashed 100% reference
  line. Consecutive present buckets are connected; a dropped bucket (missing from the map) breaks the
  line rather than being interpolated across or drawn as zero, implemented by only drawing a segment
  between `i` and `i+1` when both are non-null. Header shows the decoupling % and a
  Good/Normal/"Significant drift" label colored by `CardiacDriftBand` (green/orange/red, same visual
  language as `FatEfficiencyHistogram`'s bin colors, reordered since here green means *low* drift).
  X-axis labels are minute marks, stride-limited to ~6 labels so long rides with many buckets don't
  crowd the axis.

**`ui/screens/sessiondetail/SessionDetailScreen.kt`**
- New card inserted directly after `HeartRateZoneChart`, gated on
  `s.cardiacDriftBuckets != null && s.cardiacDriftPercent != null` — since the calculator already
  folds every other gate (ride length, power+HR presence, both-halves-have-data) into whether it
  returns null, this single non-null check is sufficient and there's no separate UI-side gating logic
  to keep in sync. No `ViewModel` changes needed; both fields ride along on the existing `session`
  `StateFlow` the same way `fatEfficiencyHistogram` does.

### Known gap
Like the `BestEffort`/power-curve data from #143/#145, `cardiacDriftBuckets`/`cardiacDriftPercent`
are computed only at import time from the raw per-record stream, which `FitImportService` discards
afterward — none of the existing 148 already-imported rides will show this card unless re-imported.
No backfill; accepted gap, consistent with the established precedent for this exact class of problem.
