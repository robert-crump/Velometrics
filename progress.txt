## Issue #169 — Rule-based ride tagging, persisted and visible
Completed: 2026-08-31

### What was done

First slice of the #167 parent (rule-based ride tagging). Auto-classifies every ride into one
of five tags — Zone 2, Intervals, Race, Recovery, Endurance — computed at import time and
persisted, so Session Detail can show a tag chip with no manual input. A timing subtlety in
`FitImportService` mattered here: `SessionMetricsCalculator.compute()` always emits
`intervalTotalTimeSec = 0` (interval detection runs afterward, power rides only), so
classifying straight off its output would make the Intervals rule permanently dead for new
imports. Classification now runs after interval detection, off a local `session.copy(
intervalCount = ..., intervalTotalTimeSec = ...)` carrying that import's real interval stats —
no extra DB round trip needed since those values are already local vars at that point.

**`domain/model/RideTag.kt`** (new) — `enum class RideTag(val label: String)`, one entry per
tag (`ZONE_2` -> `"Zone 2"`, etc.). `label`, not `name`, is what's persisted and displayed, so a
future enum-constant rename can't silently change what's already stored.

**`domain/service/RideClassifier.kt`** (new, `object`, pure — no DI, same shape as
`BestEffortCalculator`) — `classify(session: CyclingSession): RideTag`, priority order
Intervals -> Race -> Zone 2 -> Recovery -> Endurance (fallback), each rule a private predicate:
- Intervals: `intervalTotalTimeSec` is >=12% of `netDurationSec`.
- Race: zone-time majority (>=50%) in Zone 4+ *and* a steady NP:AP ("variability index") <=1.05;
  on an HR-only ride (no power meter, NP:AP unavailable) the zone majority alone qualifies,
  since NP:AP is a power-only signal with nothing to fall back to.
- Zone 2: zone-time majority (>=50%) in Zone 2.
- Recovery: zone-time majority (>=50%) in Zone 1, *or* (as a fallback when zone data doesn't
  already say so) `cardiacDriftPercent` <=3% and `fatEfficiencyScore` >=70.
- Endurance: everything else, including rides with no zone data at all.
Zone-time share prefers `powerZoneDistribution` over `hrZoneDistribution` when both exist (a
more direct effort signal); both distributions are per-datapoint counts (not percentages), so
share = matching-zone count / total count. All thresholds are an explicit best-effort starting
point per the issue — not validated against real ride history here, that's the follow-up
threshold-tuning issue's job.

**`domain/service/RideClassificationService.kt`** (new, `@Singleton`, injects
`CyclingSessionRepository`) — `reclassifyAll()`: re-runs `RideClassifier` over every session,
writing back only rows whose tag actually changed (idempotent, safe to re-run — needed by the
same follow-up issue once thresholds change). Wired into
`SettingsViewModel.recalculateAllStats()` alongside the existing `sessionComparator` loop, since
that's already the app's "recompute everything across all sessions" trigger.

**`data/local/entity/CyclingSessionEntity.kt`, `domain/model/CyclingSession.kt`,
`util/EntityMappers.kt`** — new `tag: String?` field (default `null`), round-tripped through
`toDomain()`/`toEntity()`.

**`data/local/VelometricsDatabase.kt`, `di/DatabaseModule.kt`** — schema v13 -> v14;
`MIGRATION_13_14` (`internal val`, matching `MIGRATION_11_12`'s precedent for one under test)
does `ALTER TABLE cycling_sessions ADD COLUMN tag TEXT` — classification needs domain logic, not
just SQL, so backfilling existing rows is `RideClassificationService.reclassifyAll()`'s job, not
the migration's.

**`data/local/dao/CyclingSessionDao.kt` (+ `CyclingSessionRepository`/Impl,
`FakeCyclingSessionRepository`)** — `updateTag(sessionId, tag)`, a direct
`UPDATE ... SET tag = :tag` matching `updateIntervalStats`'s existing partial-update shape
(avoids a full read-modify-write for a single-column write).

**`data/fitimport/FitImportService.kt`** — after interval detection (step 10) and before
building the summary string, computes the tag off the interval-aware local session copy and
persists it via `sessionRepository.updateTag(id, tag)`.

**`ui/screens/sessiondetail/SessionDetailScreen.kt`** — new private `RideTagChip` (an
`AssistChip` with a no-op `onClick`, matching `MapViewScreen`'s existing "Locating…" chip
precedent for a non-interactive informational chip), rendered next to the date in
`RideSummaryGrid`'s header row (`session.tag?.let { RideTagChip(it) }` — no chip at all for
older, not-yet-backfilled sessions until `reclassifyAll()` runs).

### Tests
New `RideClassifierTest` (11 cases, following `BestEffortCalculatorTest`'s pattern of a plain
constructed-fixture test, no fake repository needed since `classify` is pure): all 5 tags
individually, plus 3 explicit priority tie-break cases (Intervals beats an otherwise-qualifying
Race; Race beats an otherwise-qualifying Recovery fallback; Zone 2 beats an otherwise-qualifying
Recovery fallback), a spiky-effort case that fails Race's NP:AP check, an HR-only Race case with
no power meter, a power-vs-HR-zone preference case, and two Endurance-fallback cases (mixed zone
spread; no zone data at all). New `RideClassificationServiceTest` (2 cases, via
`FakeCyclingSessionRepository`): backfills tags onto pre-existing untagged sessions; re-running
twice corrects a stale/wrong tag and stays idempotent. New
`VelometricsMigrationTest` case (13->14): inserts a v13 row, migrates, confirms the new `tag`
column exists and reads back `NULL`. `compileDebugKotlin`, `compileDebugUnitTestKotlin`,
`assembleDebug`, full `testDebugUnitTest --rerun-tasks`: all pass (284 tests, up from 270 — 14
new), no regressions. No on-device verification this session (no
new UI interaction, just a static chip render off already-covered data; the acceptance
criteria's classification/migration/persistence logic is fully covered by the new unit and
migration tests).

## Issue #164 — Simplify: domain logic consolidation
Completed: 2026-08-30

### What was done

before this one), same shape again: fully scoped in the issue body with exact target
signatures/behaviors named, so went straight to reading every named file before editing, no
