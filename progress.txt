## Issue #151 — Ride detail: Speed distribution card is wider than the other cards
Completed: 2026-07-29

### What was done

Issue had no body/labels (picked directly per the user's explicit request, not from the
`ready-for-agent` queue — none tagged at session start). Root cause: `SpeedHistogramChartContent`'s
`Card` used a bare `Modifier.fillMaxWidth()`, unlike every sibling card on `SessionDetailScreen`
(`PowerZoneChart`, `HeartRateZoneChart`, `FatEfficiencyHistogram`, `SprintCard`, `IntervalListCard`),
which all bake `Modifier.fillMaxWidth().padding(horizontal = 16.dp, vertical = 8.dp)` directly into
their own `Card` — that's how this screen achieves consistent card margins, since `PullUpDrawer`'s
content column applies no horizontal padding of its own (each card owns its margin). The Speed
Distribution card (added in #148) missed this convention, rendering edge-to-edge and visibly wider
than its siblings.

Complication: `SpeedHistogramChartContent` is shared with `SpeedHistogramChartAvg`, used on
`RepeatedRouteDetailScreen` inside a `Column(modifier = Modifier.padding(16.dp), ...)` that already
provides margin — that screen's own `Card(modifier = Modifier.fillMaxWidth())` usages (stats/duration
estimator cards) rely on the parent column's padding and add none of their own. Simply adding the
16dp horizontal padding inside the shared Card would have double-padded that screen's card instead
(32dp inset vs. 16dp for its siblings), just moving the same bug elsewhere.

**`ui/components/SpeedHistogramChart.kt`**
- `SpeedHistogramChartContent` gained a `cardModifier: Modifier` parameter, applied to the `Card`
  instead of a hardcoded `Modifier.fillMaxWidth()`.
- `SpeedHistogramChart` (SessionDetailScreen) passes
  `Modifier.fillMaxWidth().padding(horizontal = 16.dp, vertical = 8.dp)` — matching its siblings.
- `SpeedHistogramChartAvg` (RepeatedRouteDetailScreen) passes plain `Modifier.fillMaxWidth()` —
  unchanged behavior, since that screen's parent column already pads.

## Issue #150 — Cache AllTimeStatsViewModel aggregates instead of recomputing on every load
Completed: 2026-07-27

### What was done

Only `ready-for-agent` issue in the queue; a direct follow-up to #147, which introduced the
`GlobalAverageCache` reactive-`StateFlow` pattern and filed this issue as the natural next
application of it. `AllTimeStatsViewModel` previously recomputed the entire all-time-best trio,
distance splits, power curve, per-year breakdown, and power/speed point cloud from scratch on every
screen load (`sessionRepository.getAllSessions().map { buildUiState(...) }`), including an eager
`bestEffortRepository.getAllWithSessionDate()` call inside that `map`. Applied the same
computation/cache split #147 established for `GlobalAverageCalculator`/`GlobalAverageCache`: pulled
the pure aggregation logic out into a standalone object with no ViewModel/coroutine dependencies,
then wrapped it in a singleton, app-scoped hot `StateFlow` cache, eagerly registered in
`VelometricsApplication` so computation starts at process launch rather than on first navigation.

One wrinkle `GlobalAverageCache` didn't have to deal with: this screen combines two sources
(`cycling_sessions` and `session_best_efforts`), and `FitImportService` writes them in two separate
suspend calls — session insert first, best-effort insert second (not one transaction). A cache built
by just hoisting `bestEffortRepository`'s old suspend `getAllWithSessionDate()` into a `.map` off the
sessions Flow would only ever see best-effort data current as of whenever the cache happened to
recompute, with no trigger to re-run after the second write landed. Fixed by changing
`SessionBestEffortDao.getAllWithSessionDate()` from a suspend one-shot query to a Room `Flow`-returning
query — since its SQL joins `session_best_efforts` against `cycling_sessions`, Room's invalidation
tracker re-runs it on a write to *either* table, so `combine(sessions, bestEfforts)` naturally settles
on consistent data shortly after both writes land, without any manual invalidation wiring (same
"no manual invalidation" property #147 relied on).

**`domain/model/AllTimeStatsUiState.kt`** (new)
- `RecordEntry`, `PowerCurvePoint`, `YearStat`, `PowerSpeedPoint`, `AllTimeStatsUiState` moved here
  verbatim from the ViewModel file, so the cache (`data/cache`) can depend on them without depending
  on the `ui` package — matches `RepeatedRoutesCache`/`RepeatedIntervalsCache` returning
  domain-layer types rather than UI types.

**`domain/service/AllTimeStatsAggregator.kt`** (new)
- `buildUiState(sessions, bestEfforts): AllTimeStatsUiState`, plus every private helper
  (`longestRideEntry`, `biggestClimbEntry`, `buildYearStats`, `buildPowerSpeedPoints`,
  `percentileRange`/`percentile`, `elevationBucketFor`, `splitEntry`, `powerCurvePoint`) moved
  unchanged from the ViewModel into a plain `object`, mirroring `GlobalAverageCalculator`'s shape —
  a pure function with no coroutine/DI surface, directly unit-testable.

**`data/cache/AllTimeStatsCache.kt`** (new)
- `combine(sessionRepository.getAllSessions(), bestEffortRepository.getAllWithSessionDate()) { ... }`
  through `AllTimeStatsAggregator.buildUiState`, `.stateIn(scope, SharingStarted.Eagerly,
  AllTimeStatsUiState())` — same shape as `GlobalAverageCache`.

**`data/local/dao/SessionBestEffortDao.kt`, `domain/repository/BestEffortRepository.kt`,
`data/repository/BestEffortRepositoryImpl.kt`**
- `getAllWithSessionDate()` changed from `suspend fun (): List<BestEffortRecord>` to
  `fun (): Flow<List<BestEffortRecord>>` for the reactivity reason above. `insert` untouched.

**`ui/screens/alltimestats/AllTimeStatsViewModel.kt`**
- Reduced to `val uiState: StateFlow<AllTimeStatsUiState> = cache.uiState`, no computation left —
  matches how `RepeatedRoutesViewModel`/`RepeatedIntervalsViewModel` consume their caches.

**`ui/screens/alltimestats/AllTimeStatsScreen.kt`**
- No behavior change; added imports for the four data classes now living in `domain/model` instead
  of the same package.

**`VelometricsApplication.kt`**
- New `@Inject lateinit var allTimeStatsCache: AllTimeStatsCache` alongside the other three eagerly
  registered caches.

### Tests
Moved `AllTimeStatsViewModelTest` -> `domain/service/AllTimeStatsAggregatorTest.kt`: same 9 cases,
now calling `AllTimeStatsAggregator.buildUiState(sessions, bestEfforts)` directly instead of
constructing a ViewModel with fake repositories and collecting a `StateFlow` under

one either; the pass-through wiring has nothing left to assert beyond what compilation already
guarantees. `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest
--rerun-tasks` (matching the known Gradle env-var/test-filter stale-cache quirk from #135): all
pass, no regressions.

## Issue #147 — Power/HR zone and speed distribution: all-rides average reference line
Completed: 2026-07-27

### What was done

Full /grill-me design session before implementing (issue was open-ended: "I want to calculate an
overall average over all rides... displayed in the diagrams as a thin horizontal line"). Resolved:
scope (global average shown on session-level Power/HR zone charts, plus a second reference line on
the RepeatedRoute speed histogram alongside its existing per-route average), equal-weight
normalization (average of each ride's own percentage-of-time per zone/bin, not raw seconds — a
20-minute and a 5-hour ride count equally, matching the existing per-route speed histogram average
pattern), accepted the FTP/max-HR-drift limitation (zone boundaries are baked in per-ride at import
time and raw streams aren't retained, so the average is computed over stored zone data as-is),
missing-data handling (a ride without power or HR data is skipped only for that specific average),
and the tick-mark visual (independent per-bar tick, not one continuous line, since each zone/bin
has its own average value).

Mid-session, the interview surfaced a better-fitting caching approach than the one first agreed:
this codebase already has `RepeatedRoutesCache`/`RepeatedIntervalsCache` (`data/cache/`), an
app-scoped hot `StateFlow` pattern that auto-refreshes whenever the underlying Room `Flow` emits.
Switched the plan from a DataStore-persisted cache with manual recompute-after-import/delete calls
(which would have needed a circular-dependency workaround) to the same reactive in-memory pattern
instead.

**`domain/service/GlobalAverageCalculator.kt`** (new)
- `computePowerZoneAverages`/`computeHrZoneAverages`/`computeSpeedHistogramAverages`: each ride's
  distribution is normalized to percentage-of-that-ride's-time per label first, then percentages
  are averaged equally across rides (equal weight regardless of ride length). Rides missing a given
  distribution (`powerZoneDistribution`/`hrZoneDistribution` null) are excluded from that specific
  average via `mapNotNull`, but `speedHistogram` is never null so every ride always contributes to
  that one.

**`data/cache/GlobalAverageCache.kt`** (new)
- Same shape as `RepeatedRoutesCache`: hoists `CyclingSessionRepository.getAllSessions()` into an
  app-scoped `StateFlow`, with the three averages as derived `StateFlow`s via
  `GlobalAverageCalculator`. Auto-refreshes on any DB change (import, delete) with no manual
  invalidation wiring — sidesteps a circular-DI issue a DataStore-backed approach would have hit (a
  repository depending on `CyclingSessionRepository` for reads, while
  `CyclingSessionRepositoryImpl.deleteSession` would need to call back into it).
- Registered eagerly in `VelometricsApplication` (same `@Inject lateinit var` pattern as the other
  two caches) so `SharingStarted.Eagerly` collection starts at process launch.

**`ui/components/PowerZoneChart.kt`, `HeartRateZoneChart.kt`, `SpeedHistogramChart.kt`**
- New `averagePercentages`/`allRidesAveragePercentages` parameter (default `emptyMap()`, backward
  compatible). Each bar's `Canvas` changed from a variable-height canvas (the old trick of sizing
  the Canvas itself to the bar's height) to a fixed-height canvas that manually draws a
  bottom-aligned bar rect plus an independent tick mark per bar — needed because a single average
  value can exceed what a specific ride/route's own chart would otherwise scale to. The shared
  per-chart max (`maxPct`) is computed across both the bar values and the average values so a tick
  is never clipped off the top. Tick is drawn as two overlaid `drawLine`s (a wider
  `colorScheme.surface` outline behind a narrower `colorScheme.onSurface` line) so it reads over any
  zone/bin bar color in either theme. Preserved the original 2dp minimum-visible-bar-height floor
  that the fixed-height restructuring would otherwise have dropped.

**`ui/screens/sessiondetail/SessionDetailViewModel.kt`/`Screen.kt`**
- New `powerZoneAverages`/`hrZoneAverages` `StateFlow`s sourced directly from `GlobalAverageCache`,
  collected and passed into the two zone chart composables.

**`ui/screens/repeatedroutedetail/RepeatedRouteDetailViewModel.kt`/`Screen.kt`**
- `uiState` now built via `combine(repository.getRouteById(routeId),
  globalAverageCache.speedHistogramAverages)` instead of a single `.map`; new
  `allRidesSpeedHistogram` field passed through to `SpeedHistogramChartAvg`.

Filed #150 as a related follow-up (maintainer requested during the design session): apply the same
`GlobalAverageCache`-style reactive caching to `AllTimeStatsViewModel`'s existing aggregates, which
currently recompute on every screen load — `ready-for-agent`, depends on this issue's pattern.

## Issue #144 — Add Elev. gain / 100km field to Session Detail and Repeated Route Detail
Completed: 2026-07-26

### What was done

New normalized "climb density" field so rides/routes of different lengths can be compared on
hilliness independent of distance. Grilled via /grill-me before implementing — resolved the
rounding rule (nearest-10, not ceiling), no minimum-distance threshold for short rides, null/zero
handling, the repeated-route aggregation order, and a real conflict in the original spec (it asked
for "." as a thousands separator, which collides with the app's existing Locale.US decimal-point
convention used elsewhere on the same screens).

**`util/FormatUtils.kt`**
- New `formatElevationGainPer100km(gainM, distanceKm)`: `gainM / distanceKm * 100`, rounded to the
  nearest 10m, formatted `"%,d m"` (Locale.US comma thousands separator, not the originally
  requested "." — avoids ambiguity with this file's existing decimal-point convention, e.g. a
  literal "1.500 m" reads as 1.5 m). Returns null when `distanceKm <= 0`.

**`ui/screens/sessiondetail/SessionDetailScreen.kt`**
- New "Elev. gain / 100km" `MetricCell`, placed immediately after the existing "Elevation gain"
  cell. Hidden entirely (no cell rendered) when `elevationGainM` is null or the helper returns null.

**`ui/screens/repeatedroutedetail/RepeatedRouteDetailViewModel.kt`**
- `RepeatedRouteDetailUiState` gains `elevGainPer100km: String?`, computed as
  `avg(elevationGainM over sessions with non-null data) / avgDistanceKm * 100` — averages first,
  then scales once, rather than scaling each session and averaging the ratios (avoids over-
  weighting a short outlier session in the cluster). Sessions missing elevation data are excluded
  from the gain average but still counted in the distance average, matching existing
  `avgDistanceKm` behavior.

**`ui/screens/repeatedroutedetail/RepeatedRouteDetailScreen.kt`**
- New "Elev. gain / 100km" `MetricStatCell`. Pre-implementation research had assumed the 2x3 stats
  grid had an open 6th slot — it didn't; all 6 cells (Times, Avg duration, Avg distance, Avg

  row 2 (immediately after Avg distance, honoring the original placement decision), Avg NP moves to

  matching this screen's existing convention for missing `avgPowerW`/`avgNormalizedPowerW` (session
  detail's stricter "hide the cell" rule wasn't extended here, since removing a cell from a
  weighted `Row` would misalign it against the row above).

## Issue #135 — 20km maintainer sign-off (post-#138): rejected, follow-up issues #141/#142 filed
Completed: 2026-07-15 (session outcome; #135 and #129 remain open)

### What was done

With #138 (coarse-skeleton reach=target/3 overshoot) landed and closed, re-ran the 20km leg of
#135's matrix (20km x {NONE,NORTH,EAST,SOUTH,WEST}, production graph) — the exact slice #135 was
blocked on. All 5 combos now succeed at tier `NONE` (previously 3/4 hard-failed), and `d20km_south`
(0.26 compactness) clears the calibrated `minCompactness=0.26` shape gate for the first time at
this distance, with `d20km_east` (0.25) close behind.

Rendered all 5 locally for maintainer visual review (`render_routes.py`, scratchpad-only, not
committed) — iterated the renderer per the maintainer's requests from an initial minimal-SVG
version (thicker strokes, then a 1km-grid/distance-ring offline backdrop) to a final version using
Leaflet + live OpenStreetMap tiles. Note: fetching real map tiles sends the route's bounding box
(a ~20km-wide area centered on the exact home address) to tile.openstreetmap.org over the network —
a deliberate, explicitly-confirmed exception to the standing rule of never letting anything that
embeds the home address leave the machine (previously enforced by keeping renders fully offline).
Confirmed with the maintainer before switching to live tiles.

**Maintainer verdict: none of the 5 read as a rideable oval**, including the gate-passing
`d20km_south`. Feedback, verbatim substance:
- Too many inner loops; track repeatedly moves toward the loop's center before heading back
  outward, even on the gate-passing combo. Convex-hull-based compactness doesn't catch this — hull
  area doesn't meaningfully shrink from an interior excursion as long as the outer extreme points
  are unchanged.
- `d20km_east`'s route sits mainly *west* of home, not east — direction labeling doesn't match
  actual geometry at this radius.
- `d20km_west` spends significant distance through Aachen's city center (heavy traffic) despite
  #125's hazard/stop-weighted junction costs.

Posted the full finding to #135:
https://github.com/robert-crump/Velometrics/issues/135#issuecomment-4977742372

**Scope decision (maintainer, HITL):** the shape defect (interior excursions, not caught by
compactness) and the road-choice defects (direction mislabeling, city-center routing) are different
kinds of problems — kept as two separate new issues rather than one, so neither's acceptance
criteria gets blurred (matches #129's own warning about scope-mixing after #107/#111/#113-#119):
- #141 — 20km reward-bearing corridors cut toward the loop interior, not caught by convex-hull
  compactness. Suggested starting point: check whether `LoopHull`'s `hullFactor` band clamp
  (`clamp(0.15 * meanRingRadiusM, 500, 2000)`) leaves too little relative margin at 20km-loop scale
  before adding a new interior-excursion metric; also whether intra-corridor reward-segment
  selection is unconstrained by hull bias today (only connector A* and the reward-detour pass use
  `hullFactor`).
- #142 — 20km direction-constrained routes: heading mislabeled and routed through Aachen city
  center. Suggested starting point: verify `DirectionConstraint` heading-cone filtering against
  actual generated waypoint bearings (not just anchor placement) at 20km; check whether #125's
  per-junction hazard costs aggregate correctly against cumulative urban-core exposure or need a
  distinct area-density avoidance signal.

### Net effect
#135's "sign-off at all three distances" acceptance criterion still isn't met — #138 fixed the
hard-failure/overshoot problem but not the underlying 20km shape/quality problem. #135 and #129
remain open, now blocked on #141 and #142 rather than #138. No code changes this session (pure
diagnosis + HITL sign-off); nothing to compile/test.
