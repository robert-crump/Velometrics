## Issue #164 — Simplify: domain logic consolidation
Completed: 2026-08-30

### What was done

Third `Simplify:` mechanical-cleanup issue in a row (#161/#162/#163 landed the three sessions
before this one), same shape again: fully scoped in the issue body with exact target
signatures/behaviors named, so went straight to reading every named file before editing, no
exploration subagent needed.

**`domain/service/RankedMetricEvaluator.kt`** (new, `object`) — extracted the ranking machinery
`RideMilestoneEvaluator` (#159) and `PowerCurveAchievementEvaluator` (#160) each duplicated
verbatim: `rankCandidate` (count-greater-than -> rank -> candidate-if-top-3), `startOfYear`, and
the ordinal-headline construction ("Xxx"/"2nd-Xxx"/"3rd-Xxx" + noun + "ever"/"this year"). The two
originals' headline vocab wasn't quite identical text (`RideMilestoneEvaluator` varies its base
word per metric — "longest"/"most"/"fastest"; `PowerCurveAchievementEvaluator` always uses "best")
but the *shape* was identical, so `Metric<T>` carries a per-metric `ordinalWord` field — ride
milestones pass their own varying word, power-curve metrics all pass the literal `"best"` — and
`rank(metrics, yearStart, family): List<RideRevealCandidate>` is generic over the metric's value
type (`Double` for ride milestones, `Int` for power-curve watts) so both evaluators' `countGreater`
lambda signatures still typecheck without a cast. Both evaluators now just build their own
metric-and-query list and call `RankedMetricEvaluator.rank(...)`; verified byte-identical headline
output for both by construction (same interpolated template, same word-selection logic, just
lifted to a shared function) rather than by re-deriving it from scratch.

**`SessionMetricsCalculator.compute()`** — the 6 separate `if (hasPower) ... else null` guards for
`powerZoneDistribution`/`averagePower`/`normalizedPower`/`fatBurnedGrams`/`carbsBurnedGrams`/
`fatEfficiencyHistogram`/`fatEfficiencyScore` (7 fields, `effectivePowers` itself an 8th
power-gated local feeding 4 of them) collapsed into one `computePowerMetrics(datapoints, ftp):
PowerMetrics` call behind a single `if (hasPower)`, returning a private `PowerMetrics` data class
with the same nullability each field's compute function already had (`averagePower`/
`normalizedPower`/`fatEfficiencyScore` stay `Int?`, since e.g. `computeAveragePower` can itself
return null on an empty power list; the rest are non-null). `powerQualityPercent`'s
`hasPower && datapoints.isNotEmpty()` and `cardiacDrift`'s `hasPower && avgHeartRate != null`
guards left untouched per the issue's explicit call-out — genuinely different conditions, folding
them in would change behavior. Also renamed `computePowerZones`'s shadowed `val ftp =
ftp.toDouble()` local to `ftpDouble` (pure rename, the shadowing warning is gone but the logic is
unchanged).

**`FitImportService.filterGpsQuality`** — replaced the 5 parallel `var discardSpeed`/
`discardPower`/`discardZero`/`discardLeap`/`discardImplied` counters with one
`mutableMapOf("zero" to 0, "speed" to 0, "power" to 0, "leap" to 0, "implied" to 0)`, incremented
via `discardCounts["key"] = discardCounts.getValue("key") + 1` at each of the 5 discard sites. The
final `Log.d` line's format string is untouched byte-for-byte (same `discardZero=$x,
discardSpeed=$x, ...` label text and ordering), just reading `discardCounts.getValue("zero")` etc.
instead of the old individual vars.

### Tests
No test modifications, per the issue's own acceptance criteria — `RideMilestoneEvaluatorTest`,
`PowerCurveAchievementEvaluatorTest`, and `SessionMetricsCalculatorTest` all stayed green as-is

## Issue #160 — Ride Reveal: power-curve best-effort achievements
Completed: 2026-08-29

### What was done

Only `ready-for-agent` issue in the queue — the other half of the Ride Reveal Tier 1 achievement
pair alongside #159 (ride-level milestones), which landed earlier this session and gave this one's
milestone-beats-power-curve tie-break something genuine to verify against instead of a contrived
resolver-only test. Mirrors #159's rank-query shape almost exactly ("count of best efforts with a
strictly greater value, plus 1", scoped by an optional `since` bound), applied to
`BestEffortCalculator`'s 5s/1min/5min/20min power-curve fields instead of raw session stats.

One structural difference from #159: a ride-level metric (distance, elevation, speed) lives right
on the `CyclingSession` object `RideMilestoneEvaluator.candidates()` already receives, but power-curve
bests live in a separate `session_best_efforts` row that `RideRevealEvaluator` wasn't fetching.
Added `BestEffortRepository.getForSession(sessionId)` (a single-row DAO lookup by `sessionId`, mapped
to the same `BestEffortValues` domain type the calculator already produces) so
`PowerCurveAchievementEvaluator.candidates(sessionId, sessionStart)` can look up the ride's own bests
before ranking them.

**`data/local/dao/SessionBestEffortDao.kt` (+ `BestEffortRepository`/Impl, `FakeBestEffortRepository`)**
- `getBySessionId(sessionId): SessionBestEffortEntity?` and four `countBestEffortsWithGreaterPower{5s,
  1m,5m,20m}(power, sinceEpochMs: Long?)` queries, each `SELECT COUNT(*) FROM session_best_efforts sbe
  JOIN cycling_sessions cs ON cs.id = sbe.sessionId WHERE sbe.powerX > :power AND (:sinceEpochMs IS
  NULL OR cs.sessionStart >= :sinceEpochMs)` — same join-for-the-date-scope shape #159 used, needed
  here because `session_best_efforts` itself has no date column. A NULL power value (no power meter
  that ride, or the ride was shorter than the duration) is excluded automatically by SQLite's
  NULL-comparison semantics, same as #159's NULL-elevation handling. No new index (same personal-scale
  non-issue precedent). `FakeBestEffortRepository` computes both `getForSession` and the four counts
  directly off its existing `records: MutableList<BestEffortRecord>` — that type already carries
  `sessionId`, `sessionStart`, and every power field, so no new fake-side storage was needed.

**`domain/service/PowerCurveAchievementEvaluator.kt`** (new, `@Singleton`, injects `BestEffortRepository`)
- `candidates(sessionId, sessionStart): List<RideRevealCandidate>`: fetches the ride's own best-effort
  row via `getForSession`; returns `emptyList()` outright if there isn't one (no power meter that
  ride). Builds a metric per non-null duration (5s/1m/5m/20m — up to 4, fewer if some durations are
  null e.g. a shorter ride missing 20-min), each carrying its own count-greater-than query and a
  headline label ("5-second power" etc). For each metric, queries both scopes and registers a
  `POWER_CURVE_BEST_EFFORT`-family candidate for every scope where `count + 1 <= 3` — up to 8
  candidates per ride. Headline template ("Your {best|2nd-best|3rd-best} {duration} power {ever|this
  year}!") mirrors #159's ordinal-superlative approach.

**`domain/service/RideRevealEvaluator.kt`**
- Constructor gained `PowerCurveAchievementEvaluator`; `evaluate()` now passes
  `milestoneEvaluator.candidates(session) + powerCurveEvaluator.candidates(session.id,
  session.sessionStart) + fallbackCandidate(session)` to the resolver. Class doc comment updated to
  name both Tier 1 sources as landed rather than one pending.

### Tests

## Issue #159 — Ride Reveal: ride-level milestone achievements
Completed: 2026-08-29

### What was done

Second Ride Reveal slice, picked over #160 (power-curve best-effort achievements) even though
both were unblocked by #158 landing earlier this session — #160's own acceptance criteria needs a

  `milestoneEvaluator.candidates(session) + fallbackCandidate(session)` to the resolver instead of

## Issue #158 — Ride Reveal: trigger + guaranteed fallback
Completed: 2026-08-29

### What was done

First slice of the Ride Reveal feature (design doc: `docs/ideas/ride-reveal-hero.md`, not yet
committed before this session). Picked over #159/#160 since both are explicitly blocked on this
one (they plug into the resolver/trigger this issue builds). Read the design doc's trigger-condition
section closely since it's the crux of the issue and has a subtle backfill trap: "identify the
single most-recently-imported file's ride" turns out to mean the *chronologically* newest ride
actually imported in the batch (by parsed FIT start-time), not the last file processed by name/
order — the doc's own clarifying sentence ("not filename or Dropbox processing order") only makes
sense under that reading, since `DropboxSyncService` sorts entries by filename before importing.
The backfill guard falls out for free from comparing against a *pre-sync baseline*: captured once
per batch via `getMaxSessionStart()` *before* any file in that batch is imported; a null baseline
(empty DB) means "never reveal," so a first-time Dropbox connect or fresh-install backfill of
hundreds of historical rides can't trigger it no matter which file in that batch is chronologically
last, since there's no pre-existing max to be "later than."

**`domain/repository/CyclingSessionRepository.kt` (+ Impl, DAO, `FakeCyclingSessionRepository`)**
- New `getMaxSessionStart(): Instant?` — a plain `SELECT MAX(sessionStart)`, null on an empty table.
  No new index; matches the design doc's explicit call that this is a non-issue at personal ride-
  count scale.

**`data/fitimport/ImportResult.kt`, `data/fitimport/FitImportService.kt`**
- `ImportResult.Success` gained a `sessionStart: Instant` field (the already-computed
  `session.sessionStart`, no extra DB round-trip) so callers can identify the batch's
  chronologically-newest imported ride without re-fetching every session.

**`domain/model/RideRevealCandidate.kt`** (new)
- `RideRevealScope` (ALL_TIME, THIS_YEAR), `RideRevealFamily` (RIDE_MILESTONE,
  POWER_CURVE_BEST_EFFORT, FALLBACK), and `RideRevealPriority(scope, rank, family):
  Comparable<RideRevealPriority>` implementing the design doc's exact tie-break ordering (scope,
  then rank, then family) via enum-ordinal comparison — declaring each enum's entries in
  best-first order makes the `compareTo` a one-liner per field, no explicit weight table needed.
  `RideRevealPriority.FALLBACK` is a companion constant (`THIS_YEAR`/`Int.MAX_VALUE`/`FALLBACK`)
  that's guaranteed to lose to any real 1st-3rd achievement in any scope, verified in

**`domain/service/RideRevealResolver.kt`** (new)
- `resolve(candidates: List<RideRevealCandidate>): RideRevealCandidate` — a pure `reduce` picking
  the lowest-priority (best) candidate; throws on an empty list (callers always pass at least the
  fallback).

**`domain/service/RideRevealEvaluator.kt`** (new, `@Singleton`, injects `CyclingSessionRepository`)
- `captureBaseline()`: thin wrapper on `getMaxSessionStart()`, called once per batch *before* import
  starts.
- `evaluate(results, baseline)`: null baseline -> null (backfill guard). Otherwise takes

**`ui/screens/home/HomeViewModel.kt`**
