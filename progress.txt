## Issue #233 -- Import: GPS filter for accuracy and acceleration, as in Ride-Graph
Completed: 2026-10-05

### What was done

- The filter moved out of `FitImportServiceImpl` into the pure `GpsQualityFilter` (data/fitimport),
  which returns the kept stream plus discard counts. The service only logs `result.logLine()`.
- New `Datapoint.gpsAccuracyM`, read from the FIT record's `gps_accuracy` (null when absent).
- Accuracy rule: a record with `gpsAccuracyM` > `GPS_MAX_ACCURACY_M` = 15 m is discarded. Files without
  the field are untouched.
- Acceleration rule: implied speed = haversine distance / elapsed time from the last kept record. A record
  whose |Δv| / Δt against the previous kept segment's implied speed exceeds `GPS_MAX_ACCELERATION_MPS2`
  = 5 m/s² is discarded. Gaps over `GPS_ACCELERATION_MAX_GAP_SEC` = 10 s (and zero-time steps) are
  neither checked nor used as the reference speed for the next step. Ride-Graph's `quality_filter.py`
  wasn't available locally, so the semantics follow the issue text.
- Log line: `GPS filter: kept=…, discardZero, discardSpeed, discardPower, discardAccuracy, discardLeap,
  discardImplied, discardAccel`.
- Tests (GpsQualityFilterTest): accuracy 16 m dropped / 15 m kept, missing field, a 10 m/s² GPS jump
  dropped, 4.5 m/s² braking kept, no check across an 11 s gap, a 10 s gap still checked, log counters,
  existing rules.
- DemoRideImportTest: the synthetic demo rides stop at ~7 m/s² and have GPS jitter, so 29/30 lose 1–7
  points (worst 99.84 %). The "no GPS points discarded" check is now `gpsQualityPercent >= 99.5`. The
  generator is unchanged.
- Existing rides change only after delete and re-sync.

`testDebugUnitTest` (560 tests) and `assembleDebug` pass.

## Issue #238 -- Onboarding: rider profile and Dropbox connect on first run
Completed: 2026-10-05

### What was done

- `OnboardingGate` (data/preferences) decides visibility: shown only while the new DataStore flag
  `onboarding_done` is unset and the database has no rides. An install that has rides gets the flag set
  on its first check, so an upgraded install never sees it, even after deleting its rides. The flag sits
  behind `OnboardingFlagStore` (implemented by `UserSettingsRepository`, bound in RepositoryModule).
- MainActivity: `OnboardingViewModel.visible` (null while the gate decides -> blank background) replaces
  the whole app, nav bar included, with `OnboardingScreen`. The old body is now `AppContent()`.
- Page 1 "Your profile" (`ProfileForm`, pure and tested): rider weight (default `DEFAULT_RIDER_WEIGHT_KG`
  = 75) and bike + kit (10). FTP level chips (`FtpLevel`: 2.0 / 2.6 default / 3.2 / 4.0 W/kg) with
  the live formula `2.6 W/kg × 75 kg = 195 W`. Year of birth (default current year − 40) gives a Tanaka
  max HR with the live formula `208 − 0.7 × 40 = 180 bpm`. Typing an FTP clears the level ("I know my FTP")
  so weight changes leave it alone until a level is picked again. Typing a max HR hides its formula
  until the birth year changes. Continue is disabled only if a saved field is out of range
  (`FTP_RANGE_W` 50–700, `MAX_HR_RANGE_BPM` 100–230, existing weight ranges). It saves rider/bike
  weight, max HR and the FTP as the history's "Before first test" seed row. The birth year is never stored.
- Page 2 "Connect Dropbox": Connect starts the existing OAuth flow. Onboarding finishes once
  `isConnected` turns true (result in `onResume`), so Home's auto sync starts right after. "Later"
  finishes directly. Back returns to the profile page. Either way the flag is set and Home opens.
- Tests: `ProfileFormTest` (issue examples, defaults, live FTP/max HR updates, typed overrides,
  validation), `OnboardingGateTest` (fresh install, upgrade with rides, stays hidden after deletion),
  `OnboardingFlagSettingTest` (Robolectric persistence).
- README screenshots: they import demo rides before launching, so the gate skips onboarding there.
- Not done: no visual check on a device (layout, OAuth round trip).

`testDebugUnitTest` (552 tests) and `assembleDebug` pass.

## Issue #232 -- Speed IQ: power veto and 5 km/h minimum speed drop for braking events
Completed: 2026-10-05

### What was done

- Power veto: `BrakingDetector.analyze(..., ftp)` takes the FTP in force on the ride date (ADR 0001),
  passed by `SessionMetricsCalculator` from the import's `ftpOn(rideDate)`. A step whose centred 3 s
  power (record k+1, the power covering the step) is above `SPEED_IQ_PEDAL_VETO_FTP_FRACTION` = 30 % of
  FTP gets energy 0. So it isn't braking, breaks the run (the 2 s / 1500 J minimums then apply to the
  fragments) and adds nothing to an event joined across it. Rides with estimated P (#229) and a null FTP
  skip the veto.
- Minimum speed drop: an event needs peak − low >= `SPEED_IQ_MIN_SPEED_DROP_KMH` = 5 km/h. Standing-only
  events are separate and unaffected. A dropped braking event's adjoining stop can now become a
  standing-only event if it's long enough.
- Side effect: the first coasting second after pedalling is usually vetoed (its 3 s window includes the
  pedalling), so an event's peak speed is one record later than before (44 -> 18 stop now reads 40.75 -> 18).
- Tests (BrakingDetectorTest): 200 W through a 40 -> 24 dip is an event without FTP and none at FTP 250.
  Coasting 40 -> 39 on an 8 % descent gives no event, while 40 -> 34 does. A real 44 -> 18 stop is detected
  with the veto. A ride without power with stray 400 W readings skips the veto.
- Existing rides keep their events until deleted and re-synced (no backfill, by decision). Thresholds get
  recalibrated in #231.

`testDebugUnitTest` (540 tests) and `assembleDebug` pass.


## Issue #230 -- Speed IQ: 'Show on map' marker toggle
Completed: 2026-10-04

### What was done

- "Show on map" switch in the Speed IQ card header (`SectionCard` now takes an optional `headerAction`).
  It's shown only when the ride has listed events. The state is a DataStore boolean
  (`speed_iq_show_on_map`), false until turned on, shared by every ride
  (`UserSettingsRepository.speedIqShowOnMap`, exposed by `SessionDetailViewModel`).
- Event rows are numbered `1.`–`5.`. `speedIqMarkers(speedIq, showOnMap)` (ui/components/MapSpeedIqRenderer.kt)
  turns the listed events into numbered markers at each event's lat/lon (its lowest-speed point). It returns
  nothing when the toggle is off, there's no Speed IQ, no elevation, or no events. `MapSpeedIqRenderer` draws
  them as red circles with white numbers and removes them when the list is empty.
- While on, tapping a row sets a `MapFocus` and a `DrawerSnapRequest(0.15f)`. `PullUpDrawer` gained
  `snapRequest` (animates there and reports via `onFractionSnapped`). `TrackMapWithDrawer` gained
  `focus`: it centres on that point at zoom 15 (`SPEED_IQ_FOCUS_ZOOM`) with bottom padding for the
  drawer, and goes back to fitting the track when the focus is cleared (turning the toggle off).
  While off, rows aren't clickable.
- Tests: `SpeedIqMarkersTest` (numbering/coordinates, off, no events/elevation/Speed IQ) and
  `SpeedIqShowOnMapSettingTest` (Robolectric DataStore: default off, persists for a new repository instance).
- Not done: no visual check on a device (marker look, camera padding, drawer animation).

`testDebugUnitTest` (536 tests) and `assembleDebug` pass.
