## Issue #176 — Geometric fallback for archetype merge overlap gate (road vs. adjacent bike lane)
Completed: 2026-09-02

### What was done

Follow-up to the previous session's archetype-merge work (`4a4346c`), which explicitly flagged this
as unfixable by threshold tuning alone: `IntervalClusteringService.mergeQualifies`'s overlap gate
compared map-matched edges by literal `(fromNode, toNode)` key equality, so the same physical ride
recorded once on a road and once on the adjacent bike lane/cycleway — represented as two distinct
road-graph edges — could be geometrically near-identical yet share zero edge keys, with no tolerance
setting able to catch it.

Issue #176 itself was filed `ready-for-human` with three open questions (match radius, false-merge
risk, replace-vs-supplement) rather than `ready-for-agent`; per user direction, proceeded using
proposed defaults for all three: reuse the existing `INTERVAL_POINT_MATCH_RADIUS_M` (20m) constant,
accept the parallel/frontage-road false-merge risk as a documented known limitation rather than
adding new mitigation, and have the new test run *alongside* the edge-key test (either signal
sufficient), not replace it.

**`domain/service/IntervalClusteringService.kt`** — `mergeQualifies`'s overlap gate now has a
geometric fallback, evaluated only when the edge-key test doesn't already qualify (short-circuit,
since decoding polylines is the pricier check): new `geometricOverlapRatio(candidate, longer)`
decodes both archetypes' `MapEdge.geometryEncoded` polylines to point lists (each edge already
carries its own geometry, no road-graph lookup needed), builds a `SpatialPointGrid` over `longer`'s
points at `INTERVAL_POINT_MATCH_RADIUS_M`, and computes what fraction of `candidate`'s points have a
neighbor within that radius — the same one-directional coverage-score pattern
`IntervalSimilarity.qualifies` already uses for raw GPS tracks, reused here at the edge-geometry
level per the issue's own suggested direction. `overlapOk` is now `edgeOverlapOk || geometricOverlapOk`,
both gated against the existing `INTERVAL_SUBSET_OVERLAP_THRESHOLD` (0.8). The near-miss diagnostic
log (from `4a4346c`) now reports both ratios (`edgeOverlap=... geometricOverlap=...`, `"skipped"` when
short-circuited) for on-device tuning. No `Constants.kt` changes — reuses two already-defined
constants rather than adding bike-lane-specific ones.

### Tests
Added two cases to `IntervalClusteringServiceTest`: (1) a shorter archetype whose edges use entirely
different node ids from the longer archetype's (zero edge-key overlap) but whose decoded polylines
run ~7m alongside it (well within the 20m radius) now merges — the road/bike-lane scenario the issue
describes; (2) a shorter archetype similarly edge-key-disjoint but offset ~32m away (beyond the
radius) — a genuinely separate parallel road — correctly stays unmerged, guarding against the
fallback being too permissive. `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full
`testDebugUnitTest`: all pass, 315 tests, zero failures/errors across the whole suite (aggregated
test-result XML). No on-device verification this session (no real road-vs-bike-lane duplicate pair
was available to replicate against the live DB, unlike the Camerig data pull that tuned `4a4346c`'s
length tolerance) — flagged in the issue close-out as a residual real-data validation gap, consistent
with the accepted-defaults scope for this pass.

## Issue #175 — Repeat clusters silently dropped when map-matching fails (found via #174)
Completed: 2026-09-02

### What was done

Root cause confirmed by #174's on-device investigation: `IntervalClusteringService.buildArchetype()`
returned `null` whenever `MapMatcher.match()` failed for every candidate representative in a
similarity-confirmed cluster (a short cluster whose GPS track snaps to a single, leaf-pruned road
edge, or a road-graph gap for that segment). Back in `runClustering()`, `.filterNotNull()` then
silently discarded the entire cluster — including intervals that had correctly and confidently
matched each other by GPS similarity — with no user-visible signal, only a `Log.w`.

Implemented the issue's suggested fix direction: fall back to a GPS-only archetype instead of
dropping the cluster.

**`domain/service/IntervalClusteringService.kt`** — `buildArchetype()` no longer returns `null`.
When no cluster member map-matches, it now returns a `CandidateArchetype` with `edges = emptyList()`
and `distanceM`/`startLat`/`startLon`/`endLat`/`endLon` taken directly from the median-length
member's own recorded `IntervalSession` fields (no road-matched geometry needed for these — they're
already stored per-interval). `discardSubsets()` needed no change: an edges-empty candidate never
shares edge keys with anything, so it's never mistakenly discarded as a subset.

**`data/repository/RepeatedIntervalRepositoryImpl.kt`** — `entityToDomain()` had its own copy of
the same bug: `if (edges.isEmpty()) return null` meant a GPS-only archetype (or any archetype whose
stored edge references no longer resolve against the road graph) would vanish again on every
subsequent load, even after being saved successfully. Removed that guard — an archetype with no
resolvable edges now loads fine with its name, intervals, and stats; only `edges` (and therefore the
route-line map preview, which already renders a "No GPS data available" placeholder for an empty
point list) comes back empty.

Not changed: `IntervalMatcher.archetypeTrack()` still can't match new same-route intervals against
a GPS-only archetype incrementally (no edge geometry to compare against), so such an interval waits
for the next full `runClustering()` pass — which re-clusters by GPS similarity from scratch and
will pick it up correctly. This is a temporary staleness, not the reported bug (permanent loss), so
left alone rather than inventing a synthetic edge-geometry representation to close it.

### Tests
Added `IntervalClusteringServiceTest`: a cluster whose fake matcher always returns `null` is still
saved as one archetype (both intervals grouped, `edges` empty, `distanceM`/`startLat`/`endLat` taken
from the median-length member) instead of disappearing. `compileDebugKotlin`,
`compileDebugUnitTestKotlin`, `testDebugUnitTest`: all pass, 310 tests, zero failures/errors across
the whole suite (verified via aggregated test-result XML). No on-device re-verification of the
specific reporter clusters this session (would need the same live-DB replication #174 used); the new
unit test reproduces the exact failure mode (map-matching failure on a similarity-confirmed cluster)
per the issue's own suggested repro approach.

## Issue #173 — Change heart rate zones formula
Completed: 2026-09-01

### What was done

Replaced the HR zone boundaries with Strava's formula: Zone 1|Endurance 0-109 bpm, Zone 2|Moderate
109-144, Zone 3|Tempo 144-161, Zone 4|Threshold 161-179, Zone 5|Anaerobic 179+, all against Strava's
185 bpm reference max HR. As requested, these are expressed as fractions of max HR (0%-100% scale)
rather than hardcoded bpm, so they keep working with each rider's own configured max HR setting
(`UserSettingsRepository.maxHr`), not just 185. No database bump: `hrZoneDistribution` is computed
once at import time (`SessionMetricsCalculator.computeHrZones`) and stored per-session, so already-
imported rides keep their old distribution untouched — only rides imported after this change get the
new boundaries, satisfying the issue's "new imports only" requirement with no migration needed.

**`util/Constants.kt`** — `CyclingConstants.HR_ZONES` boundaries changed from the old ad-hoc
60/70/80/90% splits to 109/185, 144/185, 161/185, 179/185 (Strava's bpm thresholds scaled by its
185 reference max HR). Zone labels ("Zone 1".."Zone 5") and `DEFAULT_MAX_HR` unchanged — only the
fraction cutoffs moved, so no other file (HR zone chart colors/labels, DB schema, JSON keys)
needed touching.

### Tests
Added `SessionMetricsCalculatorTest`: new test asserts `hrZoneDistribution` buckets bpm readings
at and just past each Strava boundary (108/109/143/144/160/161/178/179 with `maxHr = 185`) into the
expected zone. `compileDebugKotlin`, `compileDebugUnitTestKotlin`, `testDebugUnitTest`: all pass,
309 tests, zero failures/errors across the whole suite (verified via aggregated test-result XML).

## Ride tag narrative — tag-specific "main value" (user feedback, no issue filed)
Completed: 2026-08-31

### What was done

Follow-up to #171's tag-scoped narrative. User feedback: the sentence shouldn't just lead with
whichever KPI deviated most this ride — each tag has one specific metric that actually defines it,
and the sentence should always lead with that when it's available: Zone 2 → fat efficiency vs.
typical (median) fat efficiency (already existed from #171, now pinned rather than one candidate
among several); Intervals → number of intervals vs. typical number of intervals (new); Recovery →
time spent in Power Zone 1 vs. typical time in Zone 1 (new). Falls back to #171's original
deviation-ranked candidate list when the tag's main value isn't available for this ride or its
comparison pool (e.g. a Recovery ride with no power data), so there's still always a sentence
whenever there's enough tag-scoped history at all.

**`domain/model/SessionMetricSample.kt` / `data/local/dao/CyclingSessionDao.kt`
(`SessionMetricSampleEntity` + all 4 metric-sample queries) / `util/EntityMappers.kt` /
`FakeCyclingSessionRepository.kt`** — the shared metric-sample projection gained `intervalCount`
(plain column, already existed on `cycling_sessions`) and `powerZone1Sec` (read from the
`powerZoneDistribution` JSON column via `json_extract(powerZoneDistribution, '$."Zone 1"')`,
following `MapEdgeDao`'s existing json_extract precedent — no schema change, no new column).

**`domain/service/SessionComparator.kt`** — `PoolMedians`/`SessionComparison` gained
`medianIntervalCountLast5`/`AllPrevious` and `medianPowerZone1SecLast5`/`AllPrevious`, computed the
same way as the existing median fields (`intervalCount` unconditionally like duration/distance;
`powerZone1Sec` from power-having sessions only, like the other power metrics).

**`domain/service/TagComparisonNarrative.kt`** — new `mainValueCandidate(session, tag,
comparison)` maps each `RideTag` label to its designated candidate function
(`fatEfficiencyCandidate` / new `intervalCountCandidate` / new `powerZone1Candidate`, the latter
formatted via `FormatUtils.formatDuration`) and `generate()` returns it directly when non-null,
before falling through to the original deviation-ranked candidate list.

### Tests
Extended `TagComparisonNarrativeTest` (+4 cases): Zone 2 leads with fat efficiency even when
another candidate (cardiac drift) deviates more; Intervals leads with interval count when
available; Intervals falls back to deviation ranking when the interval-count median is
unavailable; Recovery leads with formatted Zone 1 time when available. Extended
`SessionComparatorTest` (+1 case): median interval count and median Zone 1 time computed correctly
from tag-scoped-style history. `compileDebugKotlin`, `compileDebugUnitTestKotlin`,
`testDebugUnitTest`: all pass, zero regressions (verified via test-result XML `failures="0"
errors="0"` across the whole suite, not just the two touched files). No on-device check this
session — pure domain/DAO-projection logic, fully covered by the unit tests above; the
`json_extract` SQL path itself isn't unit-testable in this environment (no Room in-memory DB test
infra exists in this codebase yet) but mirrors `MapEdgeDao`'s already-shipped, working usage of the
same SQLite JSON1 function and path-quoting style.

## Issue #171 — Tag-scoped comparison narrative on the ride detail screen
Completed: 2026-08-31

### What was done

Gives the tag label added in #169 (and reshaped by #170's threshold-tuning pass, see the
backfilled entry below) an expandable narrative: tapping it now shows a templated sentence
comparing this ride to the rider's own tag-scoped history, e.g. "Your cardiac drift was 2.0%,
lower than your typical 4.0% for Zone 2 rides." Also restores the label's tap affordance that
#170 dropped when it stopped being a tappable `AssistChip` (there was nothing behind it to open
at the time) — a small chevron next to the label now rotates 90° to read as an expand/collapse
control.

**`data/local/dao/CyclingSessionDao.kt` (+ `CyclingSessionRepository`/Impl,
`FakeCyclingSessionRepository`)** — tag-filtered siblings of `getSessionMetricSamplesBeforeDate`/
`getAllSessionMetricSamplesBeforeDate`: `getSessionMetricSamplesBeforeDateForTag`/
`getAllSessionMetricSamplesBeforeDateForTag`, same projection and ordering, additionally filtered
by `tag = :tag`. Also added `cardiacDriftPercent` to the shared `SessionMetricSampleEntity`/
`SessionMetricSample` projection (needed for the narrative's drift comparison) — no schema
change, the column already existed on `cycling_sessions`.

**`domain/service/SessionComparator.kt`** — `computeComparison` gained an optional
`tag: String? = null` parameter; when set, both reference pools (last-5 / all-previous) query the
tag-filtered DAO methods instead, otherwise behavior is byte-identical to before (default `null`,
all existing call sites and tests unaffected). `PoolMedians`/`SessionComparison` gained two new
metrics: `cardiacDriftPercent` (median of `SessionMetricSample.cardiacDriftPercent`) and
`npToApRatio` (median of per-ride normalizedPower/averagePower, mirroring the existing
`cardiacEfficiency` ratio-of-per-sample-values pattern) — both needed as narrative candidate
KPIs.

**`domain/service/TagComparisonNarrative.kt`** (new, pure `object`) — `generate(session, tag,
comparison)`: if the tag-scoped last-5 pool has fewer than 2 prior rides, returns "Not enough
history for {tag} rides yet." Otherwise builds up to 5 candidate KPI sentences (cardiac drift,
NP:AP ratio/power steadiness, fat efficiency score, average power, and — the one candidate never
gated on power/HR data, guaranteeing a sentence whenever there's any tag-scoped history at all —
distance) and returns whichever deviates most from its tag-scoped median by *relative* deviation
(`|current - median| / median`), so metrics on different scales (a percentage, a ratio near 1.0,
watts, km) compare fairly and the leading KPI isn't a hardcoded order.

**`ui/screens/sessiondetail/SessionDetailViewModel.kt`** — computes a second, tag-scoped
`sessionComparator.computeComparison(loaded, tag)` alongside the existing untagged one when the
session has a tag, feeds it through `TagComparisonNarrative.generate`, exposes the result as
`tagNarrative: StateFlow<String?>`. Computed eagerly in `init` alongside the existing untagged
`comparison`, matching that flow's own precedent rather than lazily on first expand.

**`ui/screens/sessiondetail/SessionDetailScreen.kt`** — `RideTagLabel` is now clickable
(`Modifier.clickable`) with an `Icons.AutoMirrored.Filled.KeyboardArrowRight` chevron that rotates
90° when expanded (the "tilted >" affordance the user asked for mid-session), toggling a local
`tagExpanded` boolean; the narrative text renders below the date/tag row only while expanded and
a narrative is actually available.

### Tests
New `TagComparisonNarrativeTest` (8 cases): not-enough-history for 0 and 1 prior same-tag rides;
leads with cardiac drift/average power/fat efficiency/NP:AP steadiness respectively when each
deviates most; falls back to the always-available distance candidate for a ride with no power or
heart-rate data; falls back to the not-enough-history text when every per-metric median is still
null despite a nonzero session count. Extended `SessionComparatorTest` (+3 cases): tag-scoped
comparison pools only same-tag sessions (verified against a mix of same-tag/other-tag/untagged
rides); a same-tag pool with only 1 prior ride still yields null medians; passing no tag is
unaffected by other tags existing in the pool. `compileDebugKotlin`, `compileDebugUnitTestKotlin`,
`assembleDebug`, full `testDebugUnitTest --rerun-tasks`: all pass (294 tests, 11 new), no
regressions. Caught and fixed a real locale bug during testing: the narrative's `String.format`
calls need explicit `Locale.US` (matching this codebase's existing `FormatUtils` convention) —
without it, a device set to a comma-decimal locale (e.g. German, already used elsewhere in this
app for date formatting) would render "2,0%" instead of "2.0%". No on-device verification this
session (pure narrative-generation/DAO-filter logic fully covered by the new unit tests; the new
chevron/expand UI is a small, visually-inspectable Compose change with no automated equivalent in
this environment).
