## Issue #134 — Return leg must diverge from the exit leg outside the 8km stem windows
Completed: 2026-07-10

### What was done

Parent #129's diagnosis flagged the exit leg (home → exit corridor) and return leg (last
corridor → home) as planned fully independently, with `ExitLegPlanner.computeReturnLeg` knowing
nothing about the exit leg's edges — on a topology with two comparable ways home, they could
retrace the same roads for their entire length rather than sharing only the first/last 8 km per
the #129 stem policy. This is the deliberately small fix: pass the exit leg's node pairs into
return-leg planning and penalize (not exclude) their reuse.

**`domain/service/ExitLegPlanner.kt`**
- `ExitLegConfig` gains `returnLegReusePenalty: Double = 5.0` — same value and same semantics as
  `RefinerConfig.edgeReusePenalty`, a soft cost multiplier rather than a hard exclusion, so a
  dead-end topology where the only road back happens to be the exit leg's road can still resolve.
- `computeReturnLeg(...)` gains `avoidNodePairs: Set<Pair<Long, Long>> = emptySet()`, threaded
  into `aStarOnEdges`. `computeExitLeg`'s own `aStarOnEdges` call is untouched (default empty
  set, no penalty) — only the return leg needs to know about the exit leg, not the reverse, since
  the exit leg is always planned first.
- `aStarOnEdges` gains the same `avoidNodePairs` param and a local `reusePenalty(edgeIdx)` closure
  applied to both the initial start-edge costs and successor relaxation, mirroring
  `RouteRefiner.shortestPathAStar`'s existing `usedNodePairs`/`edgeReusePenalty` pattern.
- New `internal fun nodePairsOf(edges: List<MapEdge>): Set<Pair<Long, Long>>` — both directions of
  every edge's node pair (road identity is direction-agnostic, same convention as
  `RouteShapeMetrics`), so callers don't need to know A*'s internal pair representation.

**`domain/service/RouteGenerator.kt`**
- `stitchRoute`'s `computeReturnLeg` call now passes
  `avoidNodePairs = ExitLegPlanner.nodePairsOf(exitLeg.edges)`.

### Tests
Two new `ExitLegPlannerTest` cases matching the issue's acceptance criteria exactly:
- `return leg avoids exit leg roads when a comparable alternate corridor exists` — a synthetic
  graph with two equal-length paths from the last corridor back home (via node 2 or node 3); the
  exit leg's node pairs cover the node-2 path, and the returned route uses none of them.
- `return leg still resolves on a single-road topology shared with the exit leg` — the only path
  home is exactly the exit leg's road; `avoidNodePairs` covers the whole path and the return leg
  still resolves (proves penalty, not exclusion).
Also `nodePairsOf includes both directions of every edge` (helper unit test).
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest`: all pass, 429 tests,
0 failures, no regressions (18 in `ExitLegPlannerTest`, up from 15).

### Harness before/after (posted to #134)
Ran `ROUTE_SHAPE_DIAGNOSIS` on the 50/80km matrix against the production graph, before (clean
pre-#134 checkout, captured earlier this session for #131/#132/#133) and after.

- **50km:** repeat fraction 0.05 → 0.00, repeated-road count 35 → 3 — the reuse penalty
  measurably cut exit/return overlap outside the stem windows. Tier (`WIDEN_BAND`) and actual
  distance (58.2 → 58.3km) essentially unchanged, so the penalty didn't push the route out of its
  distance band. Compactness dipped slightly (0.15 → 0.12, not gated by this issue) — the return
  leg now takes a marginally less direct path home to avoid the exit leg's roads, the expected
  cost of a soft penalty.
- **80km:** identical across every metric (repeat 0.01, tier `NONE`, 88.2km both runs). This run's
  return leg apparently never overlapped the exit leg's roads to begin with, matching diagnosis
  ranking this issue "secondary" — confirms the penalty is a no-op with nothing to engage on
  rather than a lucky wash.

Both runs completed (`Success`, not `Failure`) at their existing tiers — acceptance criteria met:
repeat fraction inside the stem windows unchanged (80km) or lower (50km), route still completes.

## Issue #133 — Shape-aware candidate selection and trimming via RouteShapeMetrics
Completed: 2026-07-10

### What was done

Parent #129's diagnosis found the winning candidate was picked by highest coarse reward among
in-band refined routes, with the refined route's actual shape never factoring in — a lollipop
could beat an oval on reward alone. This makes `RouteShapeMetrics` a first-class input to both
candidate selection and the mid-generation trim.

**`domain/service/RouteGenerator.kt`**
- New `RouteShapeGateConfig(minCompactness = 0.30, maxRepeatFraction = 0.15)`, both configurable,
  wired into `GeneratorConfig.shapeConfig`.
- New internal `RefinedCandidate(coarseLoop, refinedRoute, shapeReport)` replaces the previous
  `Pair<CandidateLoop, RefinedRoute>` used for the in-flight candidate pool. Every refined (and
  stitched) candidate is now scored with `RouteShapeMetrics.evaluate(finalRoute.edges,
  nodeCoords)` as soon as it's produced; `nodeCoords` comes from a new `resolveNodeCoords` helper
  (mirrors the #130 diagnosis harness's own resolver) so compactness's polyline-decode fallback
  has real coordinates to fall back to.
- `selectWinner(candidates, targetDistanceM, bandFraction, shapeConfig)`: filters to in-band
  candidates first, then prefers ones passing the shape gate (ties broken by reward), falling back
  to the highest `compactness - repeatFraction` among in-band candidates when none pass. Replaces
  the old `filter { inBand }.maxByOrNull { reward }` one-liner in `generate()`'s `Sufficient`
  branch.
- `trimRefined`: sort key extended from `(in-band, reward)` to `(in-band, gate-pass, reward)`, so
  a relaxed tier's trim can no longer discard the only shapely candidate in favor of two
  higher-reward lollipops. Marked `internal` (was `private`) so it's unit-testable directly, same
  as `selectWinner` and the new `passesShapeGate`.
- Added `shapes=[...]` and `selected ...` `Log.d` lines (compactness/repeat/gate per candidate)
  purely for harness/manual verification — no behavior change.

### Tests
Three new `RouteGeneratorTest` cases construct `RefinedCandidate`s directly (via a small
`shapeReport(compactness, repeatFraction)` + `refinedCandidate(...)` helper) to exercise
`selectWinner`/`trimRefined` in isolation, matching the issue's acceptance criteria exactly:
- `selectWinner prefers a gate-passing candidate over a higher-reward gate-failing one` — a
  reward=100 lollipop (compact 0.05, repeat 0.60) loses to a reward=10 oval (compact 0.50, repeat
  0.05).
- `selectWinner falls back to the best-shaped candidate when none pass the gate` — both candidates
  fail the gate; the one with the better `compactness - repeatFraction` wins despite lower reward.
- `trimRefined keeps a gate-passing candidate over higher-reward gate-failing ones` — trimming a
  3-candidate pool (2 high-reward lollipops + 1 low-reward oval) to `maxKeep = 1` keeps the oval.
- `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest`: all pass, 426
  tests, 0 failures, no regressions.

### Harness run (posted to #133)
Ran `ROUTE_SHAPE_DIAGNOSIS` on the 20/50/80km matrix against the production graph. Selection was
verified correct by cross-referencing each run's per-tier `shapes=[...]` log line against its
`selected ...` line: in all three runs, the tier that finally succeeded had at most one genuinely
in-band candidate (any second candidate at that tier fell outside the tier's own distance band),
so the winner was in-band-by-elimination rather than a real gate-pass-vs-reward tradeoff. None of
the three runs exercised the "gate passes, wins on reward over a higher-reward failing candidate"
path — there was never more than one in-band candidate to choose between. This mirrors #132's
finding: `CorridorOrienteer`'s coarse skeleton produces very few genuinely distinct in-band
candidates per tier on this graph (often 1-2, frequently near-duplicates), so shape-aware
selection has too small a pool to meaningfully select from yet. Candidate-pool diversity within
the accepted band is a separate, larger problem than this slice's scope (selection/trimming logic
over whatever pool exists) — flagging as a follow-up rather than expanding #133's scope. Shape
numbers themselves (0.02/0.15/0.20 compactness for 20/50/80km) are unchanged from the pre-#133
baseline, as expected since #133 only changes which candidate wins a tie and there was rarely a
tie to break on this matrix.

## Issue #132 — Adaptive coarse-distance calibration
Completed: 2026-07-10

### What was done

Parent #129's diagnosis attributed the #131 tier-cascade regression (20km/50km routes overshooting
their band, forced into looser relaxation tiers with worse candidate pools) to the coarse search
budgeting connectors at `haversine * 1.3` while #131's hull-bias makes real connector paths longer
than that assumes. This adds a one-shot recalibration: refine the first coarse candidate that
resolves, compare its real `actualDistanceM` to its own coarse `totalDistanceM`, and if the ratio is
outside +/-15%, redo the coarse search once with the target rescaled by the inverse ratio before
refining the rest of the pool.

**`domain/service/RouteGenerator.kt`**
- `effectiveTargetM` is now a `var`; the coarse-search call is factored into a local
  `runCoarseSearch(target, orienteerConfig)` closure so both the initial call and a possible
  recalibration redo share the same wiring.
- New `calibrateTarget(...)`: iterates coarse candidates until one refines successfully (matches
  #134's "first viable candidate" framing), computes `ratio = actualDistanceM / candidate.totalDistanceM`,
  and returns a rescaled target only when the ratio falls outside `CALIBRATION_TOLERANCE = 0.15`.
  Returns `attempted = false` when nothing refines (e.g. an empty coarse pool at a tight tier), so
  the generator keeps probing on the next relaxation tier instead of giving up on calibration.
- `generate()`'s tier loop gates this behind a per-call `calibrationDone` boolean set the first time
  `calibrateTarget` actually evaluates a candidate (win or lose) — guarantees at most one rescale
  redo for the whole `generate()` call, regardless of how many tiers it relaxes through afterward.
  When an exit leg exists, `effectiveTargetM` is already the corridor-loop-only budget (exit/return
  legs excluded), so rescaling it only touches the corridor loop, per the issue's scope note.

### Tests
- `RouteGeneratorTest`: `adaptive calibration reaches tier NONE despite roads that systematically
  exceed straight-line estimates` — `CorridorOrienteer` is mocked to a small deterministic stand-in
  for real fill-to-target behavior (nearest-fill-first, stop at 0.9x target) so the test controls
  candidate growth precisely without fighting the real quadrant/separation skeleton by hand;
  `RouteRefiner` runs for real over a `MeshSpokeRepository` fixture whose every direct edge is
  exactly 1.95x its geographic distance (a systemic ~1.5x inflation over the coarse `*1.3` estimate,
  matching the #129 diagnosis's cited 1.4-1.7x range) — without calibration this overshoots the
  target by ~40%, with it the recalibrated request lands ~6% under target, comfortably inside +/-15%.
- `at most one recalibration pass occurs per generation` — mocks both `CorridorOrienteer.search` and
  `RouteRefiner.refine` (`mockkObject`) so every tier's real distance stays fixed at 5x whatever
  coarse plan is requested (never lands in any band, even the widest +/-30%, so all 5 tiers relax and
  a buggy "recalibrate every tier" implementation would keep rescaling since the fixture's ratio is
  uniform). Captures every target passed to `CorridorOrienteer.search` and asserts only 2 distinct
  values appear across the whole run (the original target, and the one rescaled value) — would fail
  under a missing/broken `calibrationDone` guard.
- `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest`: all pass, no
  regressions.

### Harness before/after (posted to #132)
Ran `ROUTE_SHAPE_DIAGNOSIS` on the 20/50/80km matrix against the production graph, before (stashed
this change, clean post-#131 `main`) and after.

**Result: no visible change** — both runs produced identical output (20km: 22.7km actual, +13.7%,
`SHRINK_SEPARATION`, ~80s; 50km: 58.2km actual, +16.4%, `WIDEN_BAND`, ~280s; 80km: 88.0km, +10.0%,
`NONE`, ~81s). A temporary diagnostic log of the measured ratio explains why: on this graph the
first viable candidate's `actualDistanceM / totalDistanceM` ratio was **1.03 (20km), 1.02 (50km),
1.05 (80km)** — comfortably inside the +/-15% tolerance, so `calibrateTarget` correctly declines to
rescale every time. The connector-real-vs-coarse-estimate mismatch this issue targets isn't actually
present (post-#131) on this graph/distance matrix.

What *is* present: `CorridorOrienteer`'s own coarse `totalDistanceM` for the first 20km candidate was
already ~40.9km (`42143m actual / 1.0316 ratio`) — i.e., the coarse plan itself overshoots the target
by ~2x before any real-road refinement happens, most likely from `reach = target/3` placing quadrant
anchors near the reach boundary, whose quadrilateral perimeter is geometrically much larger than
`3 * reach`. That's a different bug from what #132 was scoped to fix (a reach/fill-ceiling sizing
mismatch, not a connector-distance-estimation mismatch) — flagging for a follow-up issue rather than
expanding #132's scope to cover it. The calibration mechanism itself is verified correct (unit tests
above) and remains a real safety net for graphs/regions where the targeted mismatch does occur; it
was simply not the dominant error source in this specific harness matrix.

## Issue #131 — Constrain glue routing to the corridor hull (LoopHull + hull-band cost)
Completed: 2026-07-10

### What was done

The core #129 fix: corridor edges were only 6-10% of a generated route, with the other ~92% being
per-segment A* glue routing with no shape objective, producing near-zero enclosed area (compactness
0.03-0.25) even when the anti-backtrack/separation machinery from #111-#119 kept literal road
repetition low. This makes glue routing trace the planned oval's perimeter instead of
shortest-pathing through its interior.

**`domain/service/LoopHull.kt`** (new)
- `LoopHull.build(points)`: convex hull (Andrew's monotone chain) over a candidate's resolved
  waypoint nodes + corridor centroids, in a local equirectangular projection anchored at the first
  point. Returns null (degenerate — no penalty) for fewer than 3 hull vertices (e.g. collinear
  input) or an enclosed area under ~1 km², preserving prior behavior for small/degenerate loops.
- `hullFactor(lat, lon, w=0.4) = 1 + w * min(ringDistM/bandM, 3)^2`, `bandM =
  clamp(0.15 * meanRingRadiusM, 500, 2000)` — exactly the design-session spec, kept as config
  defaults rather than hand-tuned. `distanceToRingM` is the perpendicular distance to the nearest
  hull boundary edge (point-to-segment, not point-to-vertex), so both cutting into the interior and
  overshooting outward the hull are penalized symmetrically.

**`domain/service/RouteRefiner.kt`**
- `refine()` builds one `LoopHull?` per candidate from `allWaypointNodes` + `candidateCorridors`
  centroids, threaded into every `shortestPathAStar` call (preload pass and the bbox-expansion
  fallback) and `rewardMaxDijkstra`.
- `shortestPathAStar`: edge cost becomes `lengthM * reusePenalty * hullFactor(edge midpoint) +
  turnCost`, applied to both the initial start-edge costs and successor relaxation. hullFactor is
  ≥1 and independent of the haversine-to-target heuristic, so the heuristic stays admissible (real
  cost only ever grows above plain length).
- `rewardMaxDijkstra`: same hullFactor applied to the length spent against the reward-detour budget
  (`effLen = lengthM * hullFactor`), so an interior-cutting detour can no longer buy the same
  amount of reward-collecting distance as a ring-hugging one. Also gained a hard exclusion
  (`usedNodePairs`) — previously this pass had no reuse guard at all and could freely route an
  out-and-back onto a high-reward edge already ridden by an earlier segment; the connector A* only
  soft-penalizes reuse via `edgeReusePenalty`, but this pass needed a hard gate since it isn't
  bounded by the A* heuristic's preference for the direct route.

### Tests
- `LoopHullTest.kt` (new): degenerate fallback (fewer than 3 points, collinear input, sub-1km²
  area all return null), a real hull for a well-separated rectangle, `distanceToRingM` zero on the
  boundary and growing toward the interior centroid, `hullFactor` exactly 1.0 on the ring and
  capping at 3 band multiples, `convexHull`/`polygonArea` unit checks.
- `RouteRefinerTest.kt`: `hull bias prefers a perimeter path over an interior chord of comparable
  length` (synthetic ~2.1km x 2.2km rectangular loop; the interior chord is 8m shorter in raw
  length but loses once hull-band cost is applied), `reward detour pass never reuses a node pair
  already used earlier in the route` (segment 2's reward detour would reuse segment 1's edge in
  reverse for identical bonus reward — hard-excluded, falls back to its own shortest path).
- `compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest` suite: all pass, no
  regressions (every pre-existing `RouteRefinerTest` case runs at a scale well under the 1km²
  degenerate-hull floor, so the whole existing suite doubles as a regression check that the
  fallback leaves untouched behavior alone).

### Harness before/after (posted to #131)
Ran `ROUTE_SHAPE_DIAGNOSIS` on the 20/50/80km matrix twice: once on a clean pre-#131 checkout
(reproduced the cited #129 baseline exactly — 0.03/0.25/0.03 compactness, confirming no drift since
diagnosis) and once with this change.
- 80km: clean win, same tier (`NONE`), compactness 0.03 -> 0.20 (~6.7x) — hull cost alone fixing
  the interior-chord problem with no other side effects.
- 20km/50km: compactness *worse* (0.03->0.02, 0.25->0.15), but via a **tier cascade**, not the hull
  cost working backwards — ring-hugging connectors are, by design, physically longer than the
  shortest path they replace (that extra length is real: `actualDistanceM` sums real edge lengths,
  unaffected by `hullFactor`). Enough connectors growing pushes a candidate that used to fit
  `DegradationPolicy`'s distance band at `NONE` out of band, forcing relaxation to a looser tier
  (wider heading cone, smaller separation) with a worse candidate pool — 50km's `NONE ->
  WIDEN_BAND` jump and 5->35 repeated roads is exactly that.
- This is the interaction #132 (adaptive coarse-distance calibration — the coarse search still
  budgets connectors at haversine x1.3, unaware #131 makes real connector paths longer) and #133
  (shape-aware candidate selection — today's tier fallback and `trimRefined` rank by reward only,
  so a relaxed tier can hand back a worse-shaped high-reward candidate) are already scoped to close.
  Shipped #131 with the design-session's exact constants (`w=0.4`, `bandM` formula) rather than
  hand-tuning against one harness run; the tier-cascade data is input for #132/#133, not evidence
  the constants are wrong.

## Issue #125 — Turn-aware junction costs from map_turns
Completed: 2026-07-06

### What was done

`JunctionCost` was orphaned — never called anywhere except its own test — and modeled turn risk
via a left-turn-vs-right-turn heuristic modulated by `MapEdge.avgStopCount`, an edge-level proxy
noted in its own comment as a stand-in until real per-turn data shipped. #123 already landed that
data (`map_turns`, `MapTurn`, `MapGraphRepository.getTurnsNear`) but nothing consumed it yet. This
wires it into the A* relaxation loop that `RouteRefiner` already runs per connector segment.

**`domain/service/JunctionCost.kt`**
- Rewrote `computeTurnCost` to take a `MapTurn?` (looked up by the caller) instead of a `MapEdge`,
  and to return a **meters-equivalent** penalty so it can be added straight onto A* g-cost
  alongside edge lengths, rather than the old 0–1-ish normalized value.
- Dropped the left-turn surcharge / `avgStopCount` waiver entirely — real per-turn hazard/stop/
  braking/ke-delta data supersedes that geometric proxy.
- New composition: when a `MapTurn` row exists, cost = angle term (unchanged bearing-difference
  penalty) + `hazardScore * hazardWeightM` + `stopPenalty * stopWeightM` +
  `(brakingProbability ?: 0.0) * brakingWeightM` + `(medianKeDelta ?: 0.0).coerceAtLeast(0.0) *
  keDeltaWeightM`. When no row exists: if the bearing change is negligible (< `negligibleAngleDeg`,
  default 5°) cost is 0 — most graph nodes are plain geometry pass-through points on a single road
  and were never written to `map_turns`, so charging every one of them would penalize routes with
  more nodes over equivalent-length routes with fewer. Only a real, unmeasured bearing change
  incurs the angle term plus a flat `unmeasuredTurnPenaltyM` surcharge for the unknown risk.
- A hazardous junction with *no* bearing change (e.g. crossing a busy road straight through) still
  costs something, since the composed-cost branch doesn't gate on angle — only the no-data branch does.

**`domain/service/RouteRefiner.kt`**
- `refine()` now preloads `repository.getTurnsNear(...)` for the same chain bbox as the edges/nodes
  preload, into a `Map<Triple<fromNode, junctionNode, toNode>, MapTurn>`.
- Waypoints alternate intra-corridor (entry→exit, reward already baked in) and connector
  (exit_i→entry_(i+1)) segments; since `buildWaypoints` always emits pairs in that order, segment
  index parity tells them apart (odd `i` = connector) with no new bookkeeping needed.
- `shortestPathAStar` gains a `turns` param (null for intra-corridor segments, the preloaded map for
  connector segments). In the successor relaxation it computes approach/exit bearings from
  `nodeMap` via the existing `GeoUtils.computeBearing`, looks up the turn keyed
  `(current.fromNode, current.toNode, succ.toNode)`, and adds `JunctionCost.computeTurnCost(...)`
  onto `newG` alongside the existing length + reuse-penalty terms.
- Scope note: the very first edge choice at a connector segment's start node isn't charged a turn
  cost (no "approach edge" carries over from the previous, independently-solved intra-corridor
  segment) — only turns strictly inside a segment's own A* search are covered. Widening that would
  require threading state across segment boundaries, which the issue didn't ask for.

### Tests
- Rewrote `JunctionCostTest.kt` for the new `MapTurn?`-based signature: angle-only monotonicity and
  wrap-around (unmeasured), each of hazard/stop/braking/ke-delta increasing cost independently,
  null braking/ke-delta treated as zero, negative ke-delta clamped to zero, a straight-through
  junction still costing something when hazard data exists, and a full sum-of-terms check against
  the default config's weights.
- `RouteRefinerTest.kt`: extended `FakeRepository` with a `turns` param feeding `getTurnsNear`. Two
  new tests on a shared fixture (direct 2→3→5 path with a hazardous turn record at the node-3
  junction vs. a longer straight 2→4→5 detour with no turn data): the connector-segment test
  asserts the detour is chosen once the hazardous turn's cost pushes the direct path above it; the
  intra-corridor-segment test (single corridor, `closeLoop = false`) asserts the same hazardous
  record is ignored and the shorter direct path wins, proving turn cost is scoped to connectors only.
- `compileDebugKotlin`, `compileDebugUnitTestKotlin`, and the full `testDebugUnitTest` suite pass
  (403 tests, 0 failures).

## Issue #128 — Follow-mode camera, locate-me fix, and accuracy circle improvements
Completed: 2026-07-05

### What was done

Two related map-marker UX fixes in `MapViewScreen.kt`, both bundled since they touch the same
user-location rendering/camera logic.

**Follow-mode camera / locate-me**
- Replaced the one-shot `fineLocationZoomedIn` flag (zoomed in once on the first accuracy ≤ 50m
  fix, then never recentered again) with a continuous `followMode` boolean. A new
  `LaunchedEffect(currentLocation, followMode, mapAndStyle)` pans the camera

- `followMode` is disabled only by a user-initiated gesture: `onMapReady` now also registers

  `startLocationUpdates()` is still called exactly once, from the permission-grant callback.

**Accuracy circle**
- `renderUserMarker`'s radius calc dropped the old 5-step accuracy binning (`10/20/50/100/200m`,
  a jitter-reduction hack) in favor of `displayRadiusM = accuracyM * 2.0` — `Location.getAccuracy()`
  is a 68%-confidence radius by definition, so doubling it approximates ~95%-confidence, making the
  dot reliably read as "inside the circle".
- Added an accuracy-weighted moving average (`LocationSample`, `LOCATION_SMOOTHING_WINDOW_SIZE = 5`)
  that smooths the *rendered* marker position only: each new `(currentLocation, locationAccuracy)`
  pair is pushed into a rolling window, and the marker is drawn at the inverse-variance-weighted
  centroid (`weight = 1 / accuracy²`) of the last 5 fixes. The canonical `currentLocation` StateFlow
  from `MapViewViewModel` is untouched, so POI-distance calculations, Fast Way Home, and the
  follow-mode camera effect above all continue to use the unsmoothed value — only
  `renderUserMarker`'s input position is smoothed.

## Test fix — RouteGeneratorTest "rejects a route whose actual distance falls outside every band"

### What was done

The test asked for a 6 km loop against the 4-corridor `LoopFixtureRepository` fixture, on the

lets `RouteGenerator.generate` legitimately assemble a real, connected ~4.6 km loop from this
fixture — which lands inside the 6 km target's widened +/-30% acceptance band ([4200, 7800]) at the
loosest degradation tier, so generation correctly returns `Success` instead of `Failure`. The test
was asserting the old (now-incorrect) upper bound, not a real defect in
`RouteGenerator`/`DegradationPolicy`/`CorridorOrienteer`.

**`RouteGeneratorTest.kt`**
- Raised the requested distance in this test from 6000.0 to 50_000.0 — the fixture's total edge
  length (corridors + connectors) is nowhere near enough to ever reach 50 km regardless of anchor

- Rewrote the comment to record both the current reasoning and why the old 6 km figure broke.

## Issue #126 — Fix stale cached location shown on app open
Completed: 2026-07-05

### What was done

`AndroidLocationSource.lastKnownFix()` used raw `LocationManager.getLastKnownLocation()` and
filtered only by accuracy, never by age — so a location cached by the OS hours earlier could be
served as "current location" on app open. This replaces the raw `LocationManager` path with
Google Play services' `FusedLocationProviderClient` and adds a 2-minute staleness filter.

**`app/build.gradle.kts` / `gradle/libs.versions.toml`**
- Added `play-services-location:21.3.0` dependency.

**`util/Constants.kt`**
- New `LOCATION_CACHE_MAX_AGE_MS = 120_000L` — cached fixes older than this are rejected.

**`data/location/AndroidLocationSource.kt`**
- Constructor now takes `FusedLocationProviderClient` (injected) alongside `Context` (still used
  for the `LocationManager` provider-enabled check that backs `LocationException.NoProvider`).
- `fixes()`: switched from per-provider `LocationManager.requestLocationUpdates` to
  `fusedLocationClient.requestLocationUpdates` with a `LocationRequest`
  (`Priority.PRIORITY_HIGH_ACCURACY`, min interval `LOCATION_UPDATE_MIN_TIME_MS`) and a
  `LocationCallback`; `awaitClose` calls `removeLocationUpdates`. `LocationSource` interface
  unchanged, so `MapViewViewModel` required no changes.
- `lastKnownFix()`: awaits `fusedLocationClient.lastLocation` (via a small `Task<T>.await()`
  suspend adapter using `suspendCancellableCoroutine` — no extra `kotlinx-coroutines-play-services`
  dependency needed) and now rejects the result if `accuracy > maxAccuracyM` **or**
  `now - location.time > LOCATION_CACHE_MAX_AGE_MS`.

**`di/LocationModule.kt`**
- Added a `@Provides` for `FusedLocationProviderClient` via
  `LocationServices.getFusedLocationProviderClient(context)`.

### Tests
New `AndroidLocationSourceTest.kt` (mockk-mocked `FusedLocationProviderClient`/`Task`/`Location`,
no Robolectric needed since every accessed method is stubbed): stale cached fix (age >
2 min) returns null; fresh cached fix (age well under 2 min) is surfaced with correct lat/lon;
a fresh-but-inaccurate fix is still rejected by the existing accuracy check; no cached location
returns null.
`compileDebugKotlin`, `compileDebugUnitTestKotlin` pass. `testDebugUnitTest`: all location/
map-view tests pass (392 tests total, 1 pre-existing unrelated failure in `RouteGeneratorTest`
confirmed present on a clean HEAD checkout before this change, not caused by it).
