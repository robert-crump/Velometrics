## Issue #128 — Follow-mode camera, locate-me fix, and accuracy circle improvements
Completed: 2026-07-05

### What was done

Two related map-marker UX fixes in `MapViewScreen.kt`, both bundled since they touch the same
user-location rendering/camera logic.

**Follow-mode camera / locate-me**
- Replaced the one-shot `fineLocationZoomedIn` flag (zoomed in once on the first accuracy ≤ 50m
  fix, then never recentered again) with a continuous `followMode` boolean. A new
  `LaunchedEffect(currentLocation, followMode, mapAndStyle)` pans the camera
  (`CameraUpdateFactory.newLatLng`, zoom preserved) to the raw `currentLocation` on every new fix
  while `followMode` is true.
- `followMode` is disabled only by a user-initiated gesture: `onMapReady` now also registers
  `map.addOnCameraMoveStartedListener`, which sets `followMode = false` when the reason is
  `MapLibreMap.OnCameraMoveStartedListener.REASON_API_GESTURE`. The app's own `animateCamera`
  calls fire with a different reason, so they don't falsely disable follow mode.
- Locate-me FAB `onClick` now sets `followMode = true` and snaps the camera to the current
  position (`newLatLngZoom`), but no longer calls `viewModel.startLocationUpdates()` — restarting
  that subscription re-triggered `lastKnownFix()`, which could momentarily overwrite the current
  position with a stale cached one (root cause of "second tap jumps back to the old city").
  `startLocationUpdates()` is still called exactly once, from the permission-grant callback.

**Accuracy circle**
- `renderUserMarker`'s radius calc dropped the old 5-step accuracy binning (`10/20/50/100/200m`,
  a jitter-reduction hack) in favor of `displayRadiusM = accuracyM * 2.0` — `Location.getAccuracy()`
  is a 68%-confidence radius by definition, so doubling it approximates ~95%-confidence, making the
  dot reliably read as "inside the circle".
- Added an accuracy-weighted moving average (`LocationSample`, `LOCATION_SMOOTHING_WINDOW_SIZE = 5`)
  that smooths the *rendered* marker position only: each new `(currentLocation, locationAccuracy)`
  pair is pushed into a rolling window, and the marker is drawn at the inverse-variance-weighted
  centroid (`weight = 1 / accuracy²`) of the last 5 fixes. The canonical `currentLocation` StateFlow
  from `MapViewViewModel` is untouched, so POI-distance calculations, Fast Way Home, and the
  follow-mode camera effect above all continue to use the unsmoothed value — only
  `renderUserMarker`'s input position is smoothed.

### Tests

anywhere in the codebase — consistent with prior map-view issues, e.g. #127). `compileDebugKotlin`,
`compileDebugUnitTestKotlin`, and the full `testDebugUnitTest` suite (38 suites, 0 failures) all

## Issue #117 — Candidate diversity via windings × alternate anchors
Completed: 2026-06-27

### What was done

`CorridorOrienteer.search()` previously built a single skeleton by selecting the one best anchor
per quadrant and returning one `CandidateLoop`. This adds two axes of diversity:

1. **CW and CCW windings** — corridors are classified into quadrants twice: once with the real
   lateral sign (clockwise oval) and once with the lateral sign negated (counter-clockwise oval),
   so Q0/Q1/Q2/Q3 map to opposite sides of the road network in each winding.
2. **Top-N anchor combos per quadrant** — `ANCHOR_COMBOS_PER_QUADRANT = 2` keeps the two
   geometry-best anchors per quadrant. All valid Cartesian-product combos (respecting the
   pairwise 2km separation rule) are enumerated via the new `enumerateAnchorCombos` recursive
   helper. Each quadrant can also contribute `null` (no anchor); all-null combos are filtered.
3. **Deduplication by corridor-set** — after each combo is anchored, empty-quadrant pseudo-
   corridors are filled, the loop is filled toward `target × 0.9`, and the sorted corridor-id
   set becomes the dedup key in `seenCorridorSets`; identical sets from the two windings are
   collapsed to one.
4. **Reward ranking** — `allResults` across both windings is sorted by `totalReward` descending
   and the top `config.candidateCount` candidates are returned.

**`domain/service/CorridorOrienteer.kt`**
- `search()` body replaced with a `for (cw in listOf(true, false))` loop.
- `arcTangentBearing(rideBearing, q, cw)` gains a `cw: Boolean = true` param; CCW negates the
  offset, flipping which side of the route each quadrant represents. All existing call sites
  (`fillEmptyQuadrantsFromEdges`, `anchorScore`) use the default, so they're unaffected.
- `anchorScore(…, cw)` similarly gains `cw: Boolean = true` and passes it to `arcTangentBearing`
  so the heading term is correct for whichever winding is being ranked.
- `private const val ANCHOR_COMBOS_PER_QUADRANT = 2` caps the combo fan-out.
- New `enumerateAnchorCombos(topPerQ, sep, nodeCoords)` — recursive Cartesian enumeration with
  separation pruning; returns `List<Array<Corridor?>>`.

**`domain/service/CorridorOrienteerTest.kt`**
- Three new tests per acceptance criteria: `search returns up to candidateCount distinct
  candidates`, `dedupe collapses identical corridor sets from both windings`, `candidates are
  ranked by descending total reward`.
- Updated two existing tests to remain stable under multi-combo ranking: the farthest anchor in
  the fill test and the NE anchor in the separation test each received explicit high rewards so
  their combos dominate the new diversity combos.

## Issue #118 — Empty-quadrant fallback via high-traversal edge pseudo-corridor
Completed: 2026-06-27

### What was done

At the tighter `reach = target / 3` radius a quadrant can end up with no qualifying anchor
corridor, leaving a gap in the oval. This adds an edge fallback: when a quadrant is empty, the
highest-`traversalCount` traversed edge in that quadrant whose heading matches the arc tangent is
turned into a pseudo-corridor and used as the quadrant anchor, so the rest of the pipeline stays
corridor-based. Quadrants with no suitable edge are skipped cleanly.

**`domain/service/CorridorOrienteer.kt`**
- `search` gains an `edgeResolver` lambda (mirrors `nodeResolver`): given a bounding box it returns
  candidate `MapEdge`s. Default no-op returns empty, so the common all-quadrants-populated path and
  every existing test resolve nothing and behave exactly as before.
- New `fillEmptyQuadrantsFromEdges` runs after anchor selection: it finds quadrants with a null
  anchor, fetches traversed edges (`traversalCount > 0`) within the reach bbox, resolves their
  endpoint coordinates once (folded into the shared `nodeCoords` map, which is now mutable), groups
  them by the quadrant of their endpoint-midpoint centroid, and for each empty quadrant picks the
  highest-traversal edge that (a) heads within the arc-tangent cone (`adequateBearing`) and (b) stays
  separated from the already-chosen anchors. The pick becomes the quadrant anchor and is added to
  `chosen` so later picks/fills honour separation against it.
- `buildPseudoCorridor(edge, id, nodeCoords)`: entry=fromNode, exit=toNode, length from the edge,
  centroid from the endpoint midpoint, `pedalReward`/`gravityReward` from the edge flow counts,
  `popularity` from `traversalCount`, `edgeList = [fromNode->toNode]` (so the separation rule and
  RouteRefiner's waypoint walk both work). Synthetic id is negative (`-(q+1)`) so it never collides
  with a positive DB corridor id. Centroid/heading derive from resolved node coords rather than
  decoding the polyline geometry — keeps the domain service free of MapLibre deps and unit-testable.
- `CandidateLoop` gains `syntheticCorridors: Map<Long, Corridor> = emptyMap()` carrying the
  synthesized pseudo-corridors; their edge-derived reward is folded into the candidate's reward.

**`domain/service/RouteGenerator.kt`**
- Wires `edgeResolver` to `repository.getEdgesNear`.
- Merges `candidate.syntheticCorridors` into the corridor map before `RouteRefiner.refine` and
  `stitchRoute`, so a pseudo-corridor resolves and routes like a real one (RouteRefiner looks
  corridors up by id in that map).

### Tests
`CorridorOrienteerTest`:
- `search synthesizes a pseudo-corridor for an empty quadrant from a high-traversal edge`
  (end-to-end: empty Q4 filled by an SE-heading edge; pseudo present in skeleton + `syntheticCorridors`).
- `search skips an empty quadrant when no suitable edge exists` (empty edge resolver -> bare anchor set).
- `search skips an empty quadrant when the only edge heads against the arc` (bearing gate rejects it).
- `buildPseudoCorridor` field mapping + null on unresolved endpoint; `adequateBearing` accept/reject
  and reject-on-unresolved. Added an `edge(...)` MapEdge helper.
- Note: tests that supply `nodeResolver` coords activate the real separation rule, so quadrant
  fixtures are spread to ±0.02deg to keep all four anchors > the 1500m adaptive separation apart.

`compileDebugKotlin`, `compileDebugUnitTestKotlin`, and the full `testDebugUnitTest` suite pass.

## Issue #119 — Re-target DegradationPolicy tiers to skeleton levers
Completed: 2026-06-26

### What was done

The relaxation loop was dead: tiers tweaked `exploreExploitBalance`/`reusePenaltyWeight` — GRASP
knobs the deterministic quadrant skeleton ignores — and `evaluate()` accepted on candidate *count*,
never on actual distance, so a loop at 0.5x or 1.5x target was returned as "success". This retargets
the tiers to the skeleton's real levers and judges acceptance on the actual refined distance.

**`DegradationPolicy.kt`**
- `RelaxationTier` renamed to the skeleton's levers, tightest-first and cumulative:
  `NONE -> WIDEN_CONE -> EXTEND_REACH -> SHRINK_SEPARATION -> WIDEN_BAND`. Each tier turns one more
  lever on and keeps the earlier ones on.
- `TierParams` now carries `headingConeCosine`, `reachFraction`, `separationM`, `distanceBandFraction`
  (was `exploreExploitBalance`/`reusePenaltyWeight`). `tierParams()` drops the GRASP base args and
  derives each lever from the tier ordinal.
- `DegradationConfig` replaces the eased-GRASP fields with base+relaxed lever values:
  cone `0.0 -> -0.5` (90deg -> 120deg), reach `1/3 -> 1/2` of target, separation `2000m -> 1000m`,
  band `0.15 -> 0.30`.
- `evaluate()` now filters candidates to those whose **actual refined distance** lands within
  `[1-band, 1+band] x target` for the current tier. Too few in-band -> request the next tier; at the
  loosest tier any in-band candidate is accepted, zero is a `HardFailure` with the existing reason.

**`CorridorOrienteer.kt`**
- `OrienteerConfig` drops the vestigial `reusePenaltyWeight` and gains the three relaxation levers
  `reachFraction`, `separationM`, `headingConeCosine` (defaults preserve prior behaviour: reach =
  target/3, sep cap = 2km, 90deg cone).
- `search()` reads `reach` from `config.reachFraction`, caps separation via
  `separationDistance(reach, config.separationM)`, and threads `config.headingConeCosine` through
  `fillToTarget -> isValidFill -> headingConsistent` (the hard heading gate on fills). The cone
  cutoff and separation cap are no longer hardcoded.

**`RouteGenerator.kt`**
- Builds the per-tier `OrienteerConfig` from the new `TierParams` (reach/separation/cone) instead of
  the dead reuse-penalty copy, and on `Sufficient` filters the refined routes to the applied tier's
  acceptance band before ranking by reward.

### Tests

  custom config, and acceptance-on-actual-distance — in-band accepted, out-of-band excluded,
  no-in-band relaxes, a route that fails tier 0 is accepted once the band widens at the loosest tier,
  partial set accepted at loosest tier, and the zero-in-band hard-failure path.
- `CorridorOrienteerTest`: heading cone widens when the cosine threshold is lowered;

## Issue #114 — 2km any-node separation rule for skeleton corridors
Completed: 2026-06-26

### What was done

**`CorridorOrienteer.kt` — adaptive any-node separation during anchor selection**
- New constants: `SEPARATION_M = 2000.0` (full air-distance minimum between any node of two
  chosen corridors) and `SEPARATION_REACH_FRACTION = 0.5`. `separationDistance(reach) =
  min(SEPARATION_M, reach * SEPARATION_REACH_FRACTION)` keeps short-target routes fillable
  (sep reaches the full 2km only at reach >= 4km, i.e. target >= 12km).
- `search()` gains a `nodeResolver: suspend (Set<Long>) -> Map<Long, Pair<Double,Double>>`
  parameter (defaults to an empty resolver so the pure scoring tests need no coordinates).
  After classifying reachable corridors into quadrants, it batch-resolves node coordinates
  **once** for every quadrant candidate (`corridorNodeIds` = entry + exit + both ends of each
  `edgeList` edge).
- Anchor selection is now **sequential and separation-aware**: each quadrant's candidates are
  ranked by the existing geometry-first `anchorScore`, and the highest-scoring candidate that
  stays separated from all previously-chosen anchors is picked. The home/start origin is the
  fixed loop endpoint and is intentionally **not** part of the spread set — anchors are kept
  apart from one another only (seeding the set with the origin would force every anchor >=2km
  from home, which is impossible for short loops and pointless since the loop returns home).
- New `corridorsSeparated(a, b, sep, nodeCoords)`: cheap centroid + half-length prefilter
  (`centroidDist > sep + lenA/2 + lenB/2` => definitely separated, no node lookup) short-circuits
  far pairs; only survivors compare resolved node lat/lon pairwise. When coordinates are
  unavailable for a near pair, the pair is treated as separated (overlap cannot be proven).

**`RouteGenerator.kt`**
- Wires `nodeResolver` to `repository.getNodesByIds(...)`, mapping each `MapNode` to its
  `(lat, lon)`. Empty id sets short-circuit to an empty map (no DB call).

### Tests
- `CorridorOrienteerTest`: cross-quadrant rejection end-to-end (a top-reward Q2 candidate whose
  node hugs the Q1 anchor is rejected in favour of a well-separated candidate), `corridorsSeparated`
  rejects overlapping parallels / accepts well-separated, prefilter short-circuits far pairs with
  no coords, unresolvable near pairs treated as separated, `separationDistance` adaptive on short
  reach, `corridorNodeIds` collects entry/exit/edge nodes.
- All existing `CorridorOrienteerTest` and `RouteGeneratorTest` cases unchanged and passing
  (fixtures carry empty `edgeList`, so separation falls back to entry/exit nodes and the tiny
  graphs still form loops).
- `compileDebugKotlin` and `testDebugUnitTest` both pass.

  2. Builds a ride-aligned frame: `rideBearing` = `direction.bearingCenter`, or — when no

     Q1) followed by the natural Q1->Q2->Q3->Q4 anchors (deduped). Returns a single
     `CandidateLoop` with summed reward/flow/discovery sub-scores and an informational coarse

## Issue #107 — Geometric bias: four-phase oval scoring in CorridorOrienteer
Completed: 2026-06-25

### What was done

**Phase-based geometric bias in GRASP construction (`CorridorOrienteer.kt`)**
- Added `geoWeight` parameter to `OrienteerConfig` (default 0.5)
- Modified GRASP candidate scoring from pure reward to reward × geometric factor:
  `geoFactor = 1.0 + geoWeight * cosineSimilarity(corridorBearing, phaseBearing)`
  `effectiveReward = (baseReward / distance) * geoFactor - reusePenalty`
- Four phases (each 25% of budget), target bearing rotates 90° per phase:
  - CW example for WEST (270°): Phase 0 → 225° (SW), Phase 1 → 315° (NW),
    Phase 2 → 45° (NE), Phase 3 → 135° (SE)
  - CCW: mirror offsets (+45, -45, -135, -225)
- CW/CCW split: even-numbered restarts use clockwise, odd use counter-clockwise
- Null direction: when `direction = null`, assigns random direction (N/E/S/W)
  per restart so routes are always oval-shaped
- `corridorBearing` computed from current route position to candidate corridor centroid
- `phaseBearing` determined from budget fraction (usedDistance / maxBudget)

**New internal helpers**
- `phaseBearing(directionBearing, clockwise, budgetFraction)`: four-phase bearing
- `geometricFactor(corridorBearing, phaseBearing, geoWeight)`: multiplicative factor
- `cosineSimilarity(bearing1, bearing2)`: cosine of angular difference

**Constants**
- `FAR_POINT_BUDGET_FRACTION = 1/3` (budget / 3 from home)
- `DIRECTIONS` array for null-direction random assignment

## Issue #101 — Surrogate lookup: find nearest parallel edge with metadata
Completed: 2026-06-24 | Closed: pending

### What was done

**New `findSurrogates()` in `GpxAnalysisUtils` (suspend, pure lookup)**
- `util/GpxAnalysisUtils.kt`: new suspend function:
  - `findSurrogates(uncoveredEdges, allEdges, spatialIndex)` — returns a
    `Map<Long, MapEdge>` mapping each uncovered edge's index to its nearest
    surrogate edge (a parallel traversed edge with speed/power metadata).
- For each uncovered edge:
  1. Decodes the edge's polyline geometry via `PolylineDecoder`.
  2. Computes the midpoint from the decoded geometry.
  3. Queries the `RTreeSpatialIndex` at the midpoint with a 20m radius.
  4. Filters candidates: must be traversed, have non-null `speedMean` and
     `powerMean`, and not be the uncovered edge itself.
  5. Computes start-to-end bearing for both the uncovered edge and each
     candidate. Keeps only candidates whose bearing difference is ≤ 45°
     (same direction only — anti-parallel edges excluded).
  6. Picks the nearest qualifying candidate by distance.

**New constants in `CyclingConstants`**
- `GPX_SURROGATE_MAX_DISTANCE_M = 20.0`
- `GPX_SURROGATE_MAX_BEARING_DIFF_DEG = 45.0`

### Tests
New `FindSurrogatesTest` with 8 tests: empty uncovered edges → empty map,
no candidates within 20m → empty map, bearing diff > 45° excluded
(perpendicular candidate), anti-parallel edges (~180° diff) excluded,
multiple qualifying candidates → nearest by distance selected, candidates
without speedMean/powerMean excluded, candidates not traversed excluded,
parallel traversed edge within range selected as surrogate (golden path).
