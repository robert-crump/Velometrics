## Issue #147 — Power/HR zone and speed distribution: all-rides average reference line
Completed: 2026-07-27

### What was done

Full /grill-me design session before implementing (issue was open-ended: "I want to calculate an
overall average over all rides... displayed in the diagrams as a thin horizontal line"). Resolved:
scope (global average shown on session-level Power/HR zone charts, plus a second reference line on
the RepeatedRoute speed histogram alongside its existing per-route average), equal-weight
normalization (average of each ride's own percentage-of-time per zone/bin, not raw seconds — a
20-minute and a 5-hour ride count equally, matching the existing per-route speed histogram average
pattern), accepted the FTP/max-HR-drift limitation (zone boundaries are baked in per-ride at import
time and raw streams aren't retained, so the average is computed over stored zone data as-is),
missing-data handling (a ride without power or HR data is skipped only for that specific average),
and the tick-mark visual (independent per-bar tick, not one continuous line, since each zone/bin
has its own average value).

Mid-session, the interview surfaced a better-fitting caching approach than the one first agreed:
this codebase already has `RepeatedRoutesCache`/`RepeatedIntervalsCache` (`data/cache/`), an
app-scoped hot `StateFlow` pattern that auto-refreshes whenever the underlying Room `Flow` emits.
Switched the plan from a DataStore-persisted cache with manual recompute-after-import/delete calls
(which would have needed a circular-dependency workaround) to the same reactive in-memory pattern
instead.

**`domain/service/GlobalAverageCalculator.kt`** (new)
- `computePowerZoneAverages`/`computeHrZoneAverages`/`computeSpeedHistogramAverages`: each ride's
  distribution is normalized to percentage-of-that-ride's-time per label first, then percentages
  are averaged equally across rides (equal weight regardless of ride length). Rides missing a given
  distribution (`powerZoneDistribution`/`hrZoneDistribution` null) are excluded from that specific
  average via `mapNotNull`, but `speedHistogram` is never null so every ride always contributes to
  that one.

**`data/cache/GlobalAverageCache.kt`** (new)
- Same shape as `RepeatedRoutesCache`: hoists `CyclingSessionRepository.getAllSessions()` into an
  app-scoped `StateFlow`, with the three averages as derived `StateFlow`s via
  `GlobalAverageCalculator`. Auto-refreshes on any DB change (import, delete) with no manual
  invalidation wiring — sidesteps a circular-DI issue a DataStore-backed approach would have hit (a
  repository depending on `CyclingSessionRepository` for reads, while
  `CyclingSessionRepositoryImpl.deleteSession` would need to call back into it).
- Registered eagerly in `VelometricsApplication` (same `@Inject lateinit var` pattern as the other
  two caches) so `SharingStarted.Eagerly` collection starts at process launch.

**`ui/components/PowerZoneChart.kt`, `HeartRateZoneChart.kt`, `SpeedHistogramChart.kt`**
- New `averagePercentages`/`allRidesAveragePercentages` parameter (default `emptyMap()`, backward
  compatible). Each bar's `Canvas` changed from a variable-height canvas (the old trick of sizing
  the Canvas itself to the bar's height) to a fixed-height canvas that manually draws a
  bottom-aligned bar rect plus an independent tick mark per bar — needed because a single average
  value can exceed what a specific ride/route's own chart would otherwise scale to. The shared
  per-chart max (`maxPct`) is computed across both the bar values and the average values so a tick
  is never clipped off the top. Tick is drawn as two overlaid `drawLine`s (a wider
  `colorScheme.surface` outline behind a narrower `colorScheme.onSurface` line) so it reads over any
  zone/bin bar color in either theme. Preserved the original 2dp minimum-visible-bar-height floor
  that the fixed-height restructuring would otherwise have dropped.

**`ui/screens/sessiondetail/SessionDetailViewModel.kt`/`Screen.kt`**
- New `powerZoneAverages`/`hrZoneAverages` `StateFlow`s sourced directly from `GlobalAverageCache`,
  collected and passed into the two zone chart composables.

**`ui/screens/repeatedroutedetail/RepeatedRouteDetailViewModel.kt`/`Screen.kt`**
- `uiState` now built via `combine(repository.getRouteById(routeId),
  globalAverageCache.speedHistogramAverages)` instead of a single `.map`; new
  `allRidesSpeedHistogram` field passed through to `SpeedHistogramChartAvg`.

Filed #150 as a related follow-up (maintainer requested during the design session): apply the same
`GlobalAverageCache`-style reactive caching to `AllTimeStatsViewModel`'s existing aggregates, which
currently recompute on every screen load — `ready-for-agent`, depends on this issue's pattern.

## Issue #138 — Coarse skeleton (reach=target/3) overshoots target before any refinement
Completed: 2026-07-15

### What was done

The #138 diagnosis (filed while closing #132) found the coarse skeleton's own `totalDistanceM`
was already ~2x the requested target before any refinement, purely from `reach = target/3`
(`CorridorOrienteer.FAR_POINT_BUDGET_FRACTION`) placing quadrant anchors near the reach boundary.
At 20km + a direction constraint this became a hard failure outright (3 of 4 direction-constrained
20km runs in #135's matrix), the last blocker keeping #135 and #129 open.

**`domain/service/CorridorOrienteer.kt`**
- `FAR_POINT_BUDGET_FRACTION` recalculated from a derivation, not tuned by hand. The coarse
  skeleton is a 5-vertex cycle `home -> Q1 -> Q2 -> Q3 -> Q4 -> home`; modeling anchors as sitting
  on the reach boundary (matching `anchorScore`'s far term, `along/reach`), evenly spaced 90deg
  apart, the expected perimeter is `reach * (2 + 2*(N-1)*sin(pi/N))` for `N=4` quadrants — the two
  home<->anchor legs plus 3 inter-anchor chords, factor `2+3*sqrt(2) ~= 6.243`. Solving for the
  fraction that lands this at `FILL_TARGET_FRACTION * target` (0.9x, not 1.0x, so `fillToTarget`
  still has headroom to add reward-bearing corridors on a typical sub-boundary anchor) gives
  `0.9 / 6.243 ~= 0.1442`, replacing the placeholder `1/3` from the original quadrant-skeleton
  design (#113-#119). The model predicted the pre-fix overshoot (6.243 * (target/3) ~= 2.08x
  target) within 2% of the #138 diagnosis's measured coarse `totalDistanceM` (~40.9km planned for
  a 20km target), which gave confidence to derive rather than hand-tune the replacement.

**`domain/service/DegradationPolicy.kt`**
- `DegradationConfig.baseReachFraction` mirrors the new `0.1442` (duplicated as a literal since
  `DegradationConfig` doesn't depend on `CorridorOrienteer`). `extendedReachFraction` (the
  `EXTEND_REACH` relaxation tier) rescaled to `0.2163`, keeping the same 1.5x ratio over base that
  the pre-#138 `0.5 / (1/3)` pair had.

### Tests

  test with one tuned to the new default.
- Most existing `CorridorOrienteerTest`/`RouteGeneratorTest` fixtures were hand-placed against the

  separation, twin orientation, candidate scoring, home snapping) — decoupled from the production

  `DegradationConfig(baseReachFraction = 1.0/3.0, extendedReachFraction = 0.5)` override rather

- `DegradationPolicyTest`: updated the hardcoded `1.0/3.0` / `0.5` expectations to `0.1442` /

## Issue #134 — Return leg must diverge from the exit leg outside the 8km stem windows
Completed: 2026-07-10

### What was done

Parent #129's diagnosis flagged the exit leg (home → exit corridor) and return leg (last
corridor → home) as planned fully independently, with `ExitLegPlanner.computeReturnLeg` knowing
nothing about the exit leg's edges — on a topology with two comparable ways home, they could
retrace the same roads for their entire length rather than sharing only the first/last 8 km per
the #129 stem policy. This is the deliberately small fix: pass the exit leg's node pairs into
return-leg planning and penalize (not exclude) their reuse.

**`domain/service/ExitLegPlanner.kt`**
- `ExitLegConfig` gains `returnLegReusePenalty: Double = 5.0` — same value and same semantics as
  `RefinerConfig.edgeReusePenalty`, a soft cost multiplier rather than a hard exclusion, so a
  dead-end topology where the only road back happens to be the exit leg's road can still resolve.
- `computeReturnLeg(...)` gains `avoidNodePairs: Set<Pair<Long, Long>> = emptySet()`, threaded
  into `aStarOnEdges`. `computeExitLeg`'s own `aStarOnEdges` call is untouched (default empty
  set, no penalty) — only the return leg needs to know about the exit leg, not the reverse, since
  the exit leg is always planned first.
- `aStarOnEdges` gains the same `avoidNodePairs` param and a local `reusePenalty(edgeIdx)` closure
  applied to both the initial start-edge costs and successor relaxation, mirroring
  `RouteRefiner.shortestPathAStar`'s existing `usedNodePairs`/`edgeReusePenalty` pattern.
- New `internal fun nodePairsOf(edges: List<MapEdge>): Set<Pair<Long, Long>>` — both directions of
  every edge's node pair (road identity is direction-agnostic, same convention as
  `RouteShapeMetrics`), so callers don't need to know A*'s internal pair representation.

**`domain/service/RouteGenerator.kt`**
- `stitchRoute`'s `computeReturnLeg` call now passes
  `avoidNodePairs = ExitLegPlanner.nodePairsOf(exitLeg.edges)`.

### Tests
Two new `ExitLegPlannerTest` cases matching the issue's acceptance criteria exactly:
- `return leg avoids exit leg roads when a comparable alternate corridor exists` — a synthetic
  graph with two equal-length paths from the last corridor back home (via node 2 or node 3); the
  exit leg's node pairs cover the node-2 path, and the returned route uses none of them.
- `return leg still resolves on a single-road topology shared with the exit leg` — the only path
  home is exactly the exit leg's road; `avoidNodePairs` covers the whole path and the return leg
  still resolves (proves penalty, not exclusion).
Also `nodePairsOf includes both directions of every edge` (helper unit test).
`compileDebugKotlin`, `compileDebugUnitTestKotlin`, full `testDebugUnitTest`: all pass, 429 tests,
0 failures, no regressions (18 in `ExitLegPlannerTest`, up from 15).
