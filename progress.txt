## Issue #230 -- Speed IQ: 'Show on map' marker toggle
Completed: 2026-10-04

### What was done

- "Show on map" switch in the Speed IQ card header (`SectionCard` now takes an optional `headerAction`).
  It's shown only when the ride has listed events. The state is a DataStore boolean
  (`speed_iq_show_on_map`), false until turned on, shared by every ride
  (`UserSettingsRepository.speedIqShowOnMap`, exposed by `SessionDetailViewModel`).
- Event rows are numbered `1.`–`5.`. `speedIqMarkers(speedIq, showOnMap)` (ui/components/MapSpeedIqRenderer.kt)
  turns the listed events into numbered markers at each event's lat/lon (its lowest-speed point). It returns
  nothing when the toggle is off, there's no Speed IQ, no elevation, or no events. `MapSpeedIqRenderer` draws
  them as red circles with white numbers and removes them when the list is empty.
- While on, tapping a row sets a `MapFocus` and a `DrawerSnapRequest(0.15f)`. `PullUpDrawer` gained
  `snapRequest` (animates there and reports via `onFractionSnapped`). `TrackMapWithDrawer` gained
  `focus`: it centres on that point at zoom 15 (`SPEED_IQ_FOCUS_ZOOM`) with bottom padding for the
  drawer, and goes back to fitting the track when the focus is cleared (turning the toggle off).
  While off, rows aren't clickable.
- Tests: `SpeedIqMarkersTest` (numbering/coordinates, off, no events/elevation/Speed IQ) and
  `SpeedIqShowOnMapSettingTest` (Robolectric DataStore: default off, persists for a new repository instance).
- Not done: no visual check on a device (marker look, camera padding, drawer animation).

`testDebugUnitTest` (536 tests) and `assembleDebug` pass.

## Issue #229 -- Speed IQ: rides without power (estimated reference power)
Completed: 2026-10-04

### What was done

- `BrakingDetector.analyze(..., estimatedReferencePowerW)`: if the estimate is given, the ride's power
  readings are ignored, so pedal work is 0 during braking, and P is the estimate.
  `SpeedIq.referencePowerEstimated` (also in the summary JSON) is true for these rides. No migration:
  Gson reads a missing boolean as false.
- Fallback for P (`BrakingDetector.estimateReferencePower`): the median of the stored per-ride P
  (`SpeedIqSummary.referencePowerW`) over the last `SPEED_IQ_FALLBACK_RIDES` = 10 power rides before
  the one being imported, else `SPEED_IQ_FALLBACK_FTP_FRACTION` = 60 % of FTP as of the ride. Power
  rides already stored their P, so no new column. New query
  `CyclingSessionDao.getPowerRideSpeedIqSummariesBefore` / `getSpeedIqReferencePowersBefore` (hasPower = 1,
  summary not null, sessionStart < ride start). Power rides imported before #226 have no P and don't count.
- `FitImportServiceImpl` computes the estimate only when `!hasPower` and passes it to
  `SessionMetricsCalculator.compute(estimatedReferencePowerW)`. Rides with power are unchanged.
- Card: an estimated P adds "No power data · braking counted at est. 165 W" under the events.
- Tests: `SpeedIqWithoutPowerImportTest` (Robolectric, real import + Room) covers the median of the last
  10 power rides before the ride (older and later rides left out), the 60 % of FTP fallback with a
  retest-dated FTP, and a power ride keeping its measured P. BrakingDetector tests check estimated P,
  that pedal work is ignored, and the median/FTP math. A SpeedIqSummary test checks the JSON round-trip.
- Not done: no visual check on a device.

`testDebugUnitTest` (532 tests) and `assembleDebug` pass.

## Issue #228 -- Speed IQ: system weight setting (as of ride)
Completed: 2026-10-04

### What was done

- Settings > Training has a "System weight (rider + bike + kit)" row after FTP. It's a DataStore int
  (`system_weight_kg`), null until set, and must be 40–200 kg (`CyclingConstants.SYSTEM_WEIGHT_RANGE_KG`).
  `NumberEditDialog` now takes a nullable current value and a valid range, and shows an error when
  the input is out of range. The row says "Not set — Speed IQ assumes 85 kg" until a weight is set.
- As of ride: `FitImportServiceImpl` reads the setting once per import and passes it to
  `SessionMetricsCalculator.compute(systemWeightKg)`, which runs the `BrakingDetector` with that mass.
  `SpeedIq.systemMassKg` is stored per ride, so changing the setting only affects later imports.
- `SpeedIq.massFromSettings` (also in the summary JSON) is false when the weight wasn't set. No
  migration: Gson reads a missing boolean as false, so rides imported before this show as assumed 85 kg.
- If the weight was assumed, the card ends with "Assumed 85 kg rider + bike + kit · Set your weight in
  Settings". Tapping it opens Settings on top of the ride.
- Tests: penalty is linear in mass (equal steps at 70/85/100 kg on a hard stop). A gentle stop isn't
  used because its last steps fall under the 150 W threshold at 70 kg. Also tested: the calculator uses
  the setting or the 85 kg default, and the summary JSON round-trips the weight, including old rows.
- Not done: no visual check on a device.

`testDebugUnitTest` (526 tests) and `assembleDebug` pass.

## Issue #227 -- Speed IQ: standing time and potential average speed
Completed: 2026-10-04

### What was done

- Standing = clock seconds below 2 km/h (record-to-record steps with both ends < 2 km/h) or with the
  FIT timer paused. The pauses are the same stop->start intervals as `pauseDurationSec`;
  `SessionMetricsCalculator.pauseIntervals` now feeds both. A step inside a pause isn't counted twice.
  Pieces closer than 5 s are one stop. A stop over 3 min (coffee stop) isn't counted at all.
- A stop belongs to a braking event when it starts < 5 s after the event's last record and doesn't
  end before the event begins. A stop with no braking is a standing-only event from 5 s (energy 0,
  speeds 0, located at the record where the stop began). Shorter ones aren't counted anywhere.
- `BrakingEvent.standingSec` and `lostSec` (penalty + standing); the top 5 are ranked by `lostSec`.
  `SpeedIq.standingSec` / `standingInTimerSec` live in the summary JSON. No migration: Gson leaves
  missing fields at 0, so rides imported before this read as 0 standing.
- `SpeedIq.potentialAvgKmh(distance, net)` = distance / (net − braking − in-timer standing).
  Standing under auto-pause is already outside net time.
- Card: `Braking 3:12 · Standing 4:40 · 17 events`, then `Avg 30.0 → 31.1 km/h without penalties`
  with an info-icon tooltip (M3 TooltipBox, shows on tap). Rows come from `speedIqEventRow`, e.g.
  `km 17.5 · 1:17 lost · 57 s braking + 20 s standing · 50→0 km/h`. A standing-only row has no speeds.
- Not done: no visual check on a device; README screenshots don't show the card.

`testDebugUnitTest` (new BrakingDetector standing tests, `SpeedIqEventRowTest`, demo rides) and
`assembleDebug` pass.

## Issue #226 -- Speed IQ: braking events card on Ride Detail (tracer bullet)
Completed: 2026-10-04

### What was done

- `BrakingDetector` (pure, domain/service): per record-to-record step,
  `E = ½m(v₁²−v₂²) + m·g·(h₁−h₂) + pedal work − drag − rolling`, with speed smoothed over 3 s and
  altitude over ~10 s (both centred). A step's P_brake = E / dt. Runs above 150 W lasting >= 2 s are
  joined across gaps < 5 s, and an event counts from 1.5 kJ. Penalty = E / P, where P = median of
  the pedalling samples (power > 0, >= 2 km/h). Record gaps > 5 s (timer pauses) split the stream.
  m = 85 kg (constant until #228); CdA 0.37, Crr 0.013, rho 1.225. All thresholds are in `CyclingConstants.SPEED_IQ_*`.
- The event km and the lowest speed come from the slowest record. The search continues past the
  event's last step while the speed keeps falling, because the last metres to a halt brake below
  the threshold. The peak is the fastest record before the slowest one.
- `CyclingSession.speedIq` is computed in `SessionMetricsCalculator` (power rides only) and stored
  as two JSON columns, `speedIqSummary` and `speedIqEvents` (top 5), in Room v24 (MIGRATION_23_24).
  Import-time only, no backfill. A ride without altitude stores `hasElevation=false`.
- Ride Detail drawer: a "Speed IQ" section card after Speed: `Braking 1:13 · 4 events`, then rows
  like `km 10.1 · 31 s braking · 42→0 km/h`, or "No elevation data". No card when `speedIq` is null
  (no power, or imported before this change).
- Demo rides: 2–13 events each, with stops and the same corners recurring per loop.
- Deviation: with this formula, #223's worked example (85 kg, −5 %, 50→0 km/h in 15 s) gives
  ≈ 9.1 kJ / ≈ 48 s, not ≈ 10.9 kJ / 57 s. Drag over the stop is ~2.3 kJ. The test asserts 9.1 kJ.
- Not done: no visual check on a device; README screenshots don't show the card yet.

`testDebugUnitTest` (incl. `BrakingDetectorTest`, migration 23->24, demo ride Speed IQ) and
`assembleDebug` pass. The first test run hit a one-off native Robolectric crash
(libandroid_runtime finalizer); the rerun was clean.
