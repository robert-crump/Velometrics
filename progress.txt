## Issue #182 — Spin out HRR60 into its own card, with power figure + info overlay
Completed: 2026-09-06

### What was done

Split heart-rate recovery display out of the Interval Card into a dedicated card, and surfaced
`avgPower60sAfter` (persisted since #178 but never shown anywhere).

**`ui/components/Hrr60Card.kt`** (new) — `Hrr60Card(intervals)` composable. Returns immediately
(renders nothing, no empty-state placeholder) when no interval has a non-null `hrr60`. One row per
interval with a non-null `hrr60`: interval number, `-N bpm` HRR60, and `avgPower60sAfter` in W (or
"—" if that field is null for some reason while hrr60 isn't). Both figures get the identical
truncation marker (asterisk + `onSurfaceVariant` color) when `restBeforeNextIntervalSec < 60`,
since they're computed over the same forward-looking window — previously only HRR60 carried the
marker. Title row has an "i" `IconButton` (`Icons.Filled.Info`) that opens an `AlertDialog`
(same pattern as `HomeScreen`'s small-file-warning dialog) explaining what HRR60 measures (HR drop
in the 60s after an interval, bigger = better parasympathetic recovery) and what the accompanying
power figure means (near-zero suggests coasting, elevated suggests continued/soft-pedaling effort)
plus what the asterisk means. `hrr30`/`avgPower30sAfter` are not referenced anywhere in this card —
left unsurfaced per the issue's explicit scope.

**`ui/components/IntervalListCard.kt`** — removed the inline `interval.hrr60?.let { ... }` `Text`
block (moved, not duplicated) from the per-interval row.

**`ui/screens/sessiondetail/SessionDetailScreen.kt`** — `Hrr60Card(intervals = intervals)` added
directly after `IntervalListCard`, inside the same `s.hasPower && intervals.isNotEmpty()` guard
(consistent with the interval list itself only ever showing for power-having sessions); the card's
own internal "any interval has hrr60" check is what actually decides whether it renders anything.

## Issue #181 — Interval Card decluttering, drop normalized time & interval count from header
Completed: 2026-09-06

### What was done

Pure display-consistency fix: `durationNormalizedSec` (FTP-normalized duration) was being shown or
used for coloring in several places that read as if they were reporting plain elapsed time, which
was misleading (and, for the map legend vs. actual rendered color, an outright mismatch since the
two could disagree once an interval's FTP-normalized duration diverged from its raw one).

**`ui/components/IntervalListCard.kt`** — removed the "(norm: …)" secondary `Text` per interval
row entirely (was only shown when `durationNormalizedSec != durationSec`). Header changed from

**`ui/screens/repeatedintervaldetail/RepeatedIntervalDetailScreen.kt`** — the History row's

label actually says.

**`ui/components/MapIntervalRenderer.kt`** (`renderUngroupedIntervals`) — the per-interval map

Left alone, per the issue's explicit scope: `MapViewScreen`'s interval-tap popup (still shows raw

of these were named in the issue's acceptance criteria and each lives in a different screen context
than the legend/renderer pair being fixed.

A mid-task user note suggested the map legend should derive its bucketing from the user's FTP
setting rather than fixed thresholds; confirmed with the user this was out of scope for this issue
(the whole point of #181 is that these labels describe *plain* duration, not an FTP-normalized
figure) and proceeded with the issue as written.

## Issue #184 — Fix Repeated Interval auto-numbering collisions (self-healing renumber)
Completed: 2026-09-06

### What was done

Bug-fix pass on `IntervalClusteringService.runClustering()`'s default-name assignment. Root cause:
the naming counter for archetypes that don't match an existing entry (`counter = 1`) reset to 1 on
every run — a run's *own* unmatched archetypes stayed sequential within that run, but two different
runs, each starting from 1, could hand out the same number to two different archetypes over many
pull-to-refreshes, and never converged back to something sequential. Matched production symptom:
duplicate/scattered default names like "Repeated Interval 36", "28", "27", "22".

**`domain/service/IntervalClusteringService.kt`** — restructured the naming section into two
pieces, both keyed off a new `DEFAULT_NAME_PATTERN = Regex("""^Repeated Interval (\d+)$""")` /
`defaultNameNumber()` helper that tells a default-assigned name apart from a custom one (e.g.
"Schlangenweg"):
- **Self-heal, unconditional, every run:** before any name is carried forward from `existing`,
  every default-named row already in the DB is renumbered — sorted by its *current* (possibly
  colliding/scattered) number ascending, reassigned sequential 1, 2, 3, ... via a
  `healedNameById` map keyed by row id. Custom names never match the pattern, so they're excluded
  from the sort and left completely untouched. This runs whether or not a collision is currently
  present, so default names stay clean going forward rather than only once damage is detected.
- **Anti-collision counter seed:** the counter used for a genuinely new (unmatched) archetype now
  starts at `defaultOrderedExistingIds.size + 1` (one past the post-heal max) instead of a
  hardcoded `1`, so a fresh archetype can never reuse a number the self-heal pass (or an earlier
  run) already assigned to something else.
- `newEntries`'s existing-match step now looks up `healedNameById[matchedExisting.id]` instead of
  `matchedExisting.name` directly, so a carried-over archetype's name reflects the healed number,
  not the raw (possibly colliding) DB value.

### Tests
Two new cases added to `IntervalClusteringServiceTest`, both driving the full `runClustering()`
pipeline (mocked repositories) rather than a unit-isolated helper, matching this file's existing
style:
- `a genuinely new archetype's default name is seeded above the existing max, not restarted at 1`
  — existing DB has two already-clean default entries (1, 2); one is carried forward this run, the
  other goes stale (its interval no longer present); a third, genuinely new interval produces an
  unmatched archetype. Asserts the carried entry keeps "Repeated Interval 1" and the new one gets
  "Repeated Interval 3" — the old bug would have handed the new one "Repeated Interval 1" too,
  colliding with the still-live carried entry.
- `pre-existing scattered or colliding default names are self-healed into a clean sequential
  renumbering` — reproduces the production symptom directly: three carried-forward default rows
  named "27", "22", "22" (an outright duplicate) plus one custom-named row ("Schlangenweg").
  Asserts the three default rows come out as a clean "1", "2", "3" (ordered by their prior number,
  ties broken by original list order) and the custom row is completely unchanged.

`compileDebugKotlin`, `compileDebugUnitTestKotlin`, `assembleDebug`, full `testDebugUnitTest`: all
pass, 327 tests, zero failures/errors (aggregated test-result XML; 325 prior + 2 new). No on-device
verification this session (no emulator/device attached) — this is pure in-memory naming/sorting
logic over mocked repositories, fully covered by the new tests, so the residual gap is the same
kind already accepted for prior sessions in this file (e.g. #178/#179/#176).
